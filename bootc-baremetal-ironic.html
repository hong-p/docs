01

왜 바꾸나 · qcow2의 세 가지 마찰

베어메탈(bare metal)은 가상 머신이 아닌 실제 서버입니다. 서버의 빈 디스크에 운영체제를 설치하고, 그 서버를 원하는 상태로 맞추는 일을 프로비저닝이라고 합니다. 발표는 이 작업이 빌드·배포·운영의 세 지점에서 불편하다고 말합니다.

qcow2는 무엇인가?

qcow2는 QEMU(Quick Emulator)의 Copy On Write version 2 형식으로 만든 가상 디스크 이미지입니다. 완성된 하드디스크를 통째로 복사해 둔 파일이라고 생각하면 쉽습니다. 베어메탈에 쓸 때는 이 파일의 내용을 실제 디스크에 풀어 써야 합니다.

01 · 빌드

만드는 도구와 설계가 복잡하다

qcow2를 만들려면 디스크 이미지 전용 툴링과 파티션 레이아웃을 정해야 합니다. 컨테이너 빌드 파이프라인과 자연스럽게 이어지지 않습니다. 서버 제조사나 펌웨어 요구가 달라지면 같은 파일을 그대로 쓰기 어렵습니다.

02 · 배포

큰 파일을 별도 경로로 옮긴다

파일이 크므로 배포가 번거롭습니다. HTTP(Hypertext Transfer Protocol)는 웹에서 파일을 주고받는 통로이지, 이미지의 메타데이터·버전·체크섬을 함께 관리하는 구조화된 이미지 API가 아닙니다. Glance 같은 서비스도 자기 OpenStack 클라우드 안에 묶일 수 있습니다.

03 · 운영

시간이 지나면 서버가 달라진다

서버를 수동으로 고치면 원하는 기준 상태에서 조금씩 벗어나는 드리프트가 생깁니다. 변경이 위험하고, 문제가 생겼을 때 이전 상태로 되돌리는 롤백도 어렵습니다. 이미지가 있어도 운영체제의 수명주기 관리 문제는 남습니다.

문제의 핵심

qcow2는 단순히 “큰 파일”이라서만 불편한 것이 아닙니다. 만드는 방식, 옮기는 통로, 설치된 뒤의 상태 관리가 서로 다른 도구와 경로로 갈라져 있습니다. 발표의 해법은 이 세 지점을 하나의 이미지 경험으로 묶는 것입니다.

02

그래서 뭘 바꾸나 · bootc로 OS를 이미지화하기

bootc는 “OS 전체를 담은 컨테이너 이미지”다

bootc는 이미지 모드 리눅스(Image Mode Linux)를 위한 도구입니다. 여기서 컨테이너는 프로그램과 실행에 필요한 파일을 묶어 격리된 환경에서 실행하는 단위이고, 컨테이너 이미지는 그 환경을 저장·배포하는 파일 묶음입니다. bootc는 이 아이디어를 앱 하나가 아니라 부팅 가능한 운영체제 전체에 적용합니다.

OCI(Open Container Initiative)는 컨테이너 이미지 형식과 런타임의 개방형·벤더 중립 산업 표준입니다. RHEL(Red Hat Enterprise Linux) Image Mode는 RHEL 운영체제를 OCI 이미지처럼 만들고 관리하는 방식이며, bootc가 그 설치와 업데이트를 담당합니다. VM(Virtual Machine)은 한 물리 서버 안에 소프트웨어로 만든 별도의 컴퓨터입니다. 따라서 이미 앱 팀이 쓰는 buildah나 Dockerfile, 레지스트리와 태그를 OS 팀도 재사용할 수 있습니다.

이전의 기준

디스크 파일 중심

  • qcow2를 별도로 빌드하고 서버에 풀어 쓴다.
  • 파티션과 하드웨어 전제를 파일 안에 고정한다.
  • 변경 뒤의 서버 상태를 다시 이미지와 맞추기 어렵다.
bootc의 기준

이미지와 상태 중심

  • 표준 이미지 빌드 도구로 OS 이미지를 만든다.
  • 컨테이너 레지스트리를 앱스토어처럼 사용한다.
  • 원자적 업데이트와 롤백으로 한 번에 상태를 바꾼다.
  • 읽기 전용 /usr로 기본 OS를 보호한다.
앱 컨테이너와 같은 겉모습, 다른 목적

bootc 이미지도 매니페스트와 레이어를 가진 OCI 이미지입니다. 하지만 앱 프로세스 하나를 실행하는 용도가 아니라, 커널부터 부팅 서비스까지 갖춘 컴퓨터 한 대의 운영체제를 표현합니다. 이 차이를 이해하면 “컨테이너 이미지로 베어메탈을 부팅한다”는 문장이 과장이 아니라는 것을 알 수 있습니다.

03

컨테이너 이미지 구조를 비교하기

이미지 레지스트리는 컨테이너 이미지를 보관하고 내려주는 저장소입니다. 앱스토어가 앱의 이름·버전·다운로드 파일을 한데 관리하듯, 레지스트리는 이미지의 주소와 버전을 관리합니다. JSON(JavaScript Object Notation)은 매니페스트와 컨피그처럼 구조화된 정보를 적는 텍스트 형식입니다. 발표는 같은 저장 인프라를 세 가지 내용물에 적용해 비교합니다.

01 · 표준 OCI 이미지

앱을 실행하는 상자

manifest.json
config.json
layer-1.tar
layer-2.tar
layer-3.tar

매니페스트(manifest)는 이미지가 어떤 파일로 구성됐는지 가리키는 목차입니다. 컨피그(config)는 실행 설정이고, 레이어(layer)는 파일시스템의 겹입니다. JSON(JavaScript Object Notation)은 이 메타데이터를 표현하는 구조화된 텍스트 형식입니다. 애플리케이션과 런타임 의존성만 담고 컨테이너 런타임 안에서 프로세스로 실행되도록 설계됩니다.

02 · bootc 이미지

부팅 가능한 OS 상자

manifest.json
config.json
layers...
  ├─ kernel
  ├─ systemd
  ├─ grub
  ├─ shim
  └─ /usr

겉 구조는 표준 OCI 이미지와 같습니다. 다만 커널, systemd(리눅스 서비스의 시작·감독을 맡는 시스템 관리자), grub/shim(OS를 시작하는 부트로더와 보조 부트로더)까지 포함한 완전한 OS입니다. 내장된 bootc 도구가 qcow2 생성이나 블록 디바이스 직접 쓰기처럼 설치 대상에 맞는 작업을 합니다.

03 · OCI 아티팩트

레지스트리에 파일을 얹는 상자

manifest.json
artifact: os-image.qcow2

OCI 아티팩트는 컨테이너가 아닌 임의의 결과물을 OCI 레지스트리에 저장하는 방식입니다. ORAS(OCI Registry As Storage) 도구로 qcow2를 매니페스트와 함께 올릴 수 있어 구조가 단순합니다. 하지만 qcow2를 빌드하고 운영체제 상태를 관리해야 하므로 배포 문제만 해결합니다.

중요한 선 긋기

OCI 아티팩트는 “qcow2를 어디에 잘 보관하고 가져올까?”에 대한 답입니다. bootc는 “qcow2 자체를 만들지 않고 OS를 어떻게 빌드·업데이트할까?”에 대한 답입니다. 둘은 같은 레지스트리를 사용할 수 있지만 해결하는 문제의 범위가 다릅니다.

04

OpenStack Ironic에 들어간 변경

이제 이미지가 실제 서버에 닿는 길을 봅니다. Kubernetes(쿠버네티스)는 컨테이너와 인프라의 원하는 상태를 선언하고 맞추는 오케스트레이터입니다. Metal3는 그 선언을 받아 베어메탈을 쿠버네티스 방식으로 관리하고, 내부에서 OpenStack Ironic을 사용합니다. CNCF(Cloud Native Computing Foundation)는 클라우드 네이티브 오픈소스 프로젝트를 지원하는 재단입니다.

OpenStack Ironic

서버 설치 담당자

Ironic은 OpenStack의 BMaaS(Bare Metal as a Service) 구성요소입니다. 클라우드에서 가상 머신 대신 실제 서버를 할당하고 디스크에 이미지를 써 주는 역할을 합니다.

Metal3 · “metal cubed”

쿠버네티스식 베어메탈 관리

Metal3는 CNCF 인큐베이팅 프로젝트입니다. CRD(Custom Resource Definition)로 정의된 커스텀 리소스를 통해 서버의 상태를 선언하고, OpenShift 클러스터와 범용 BMaaS 환경을 관리합니다.

Red Hat 제품 연결

OCP 위의 RHOSO

OCP(OpenShift Container Platform)는 Red Hat의 쿠버네티스 플랫폼입니다. RHOSO(Red Hat OpenStack Services on OpenShift)는 OCP 위에서 컨트롤 플레인을 운영하고, IaaS(Infrastructure as a Service) 방식으로 데이터플레인 컴퓨트 노드를 베어메탈로 프로비저닝하는 OpenStack 클라우드입니다.

노드 안에서 실제로 쓰는 작업자

IPA(ironic-python-agent)는 베어메탈 서버에서 실행되는 Ironic 에이전트입니다. 지시받은 이미지를 가져와 디스크에 쓰고, 설치 결과를 Ironic에 보고합니다. 이 발표의 변화는 IPA가 qcow2 HTTP 파일만 받는 데서 벗어나 bootc OCI 이미지도 직접 처리할 수 있게 된다는 데 있습니다.

autodetect가 이미지 유형을 보고 deploy 인터페이스를 고릅니다. OCI 아티팩트 처리도 개선됩니다.

Hibiscus · 2026.2

autodetect 개선

발표가 설명한 다음 개선 지점입니다. 설정은 그대로 두고 이미지 종류에 따른 선택을 더 안정적으로 맡길 수 있습니다.

bootc 없이 쓰는 일반 설정

기존 방식은 기본 배포 인터페이스를 direct로 둡니다. direct는 qcow2 같은 디스크 이미지를 직접 내려받아 쓰는 경로입니다.

[DEFAULT]
default_deploy_interface = direct
enabled_deploy_interfaces = direct,fake,ramdisk,custom-agent

autodetect로 bootc 켜기

새 설정에서는 autodetect를 기본값으로 둡니다. URL(Uniform Resource Locator)은 이미지가 있는 주소를 뜻합니다. 사용할 후보에 bootc를 넣으면 Ironic이 이미지 주소와 내용에 따라 경로를 선택합니다.

[DEFAULT]
default_deploy_interface = autodetect
autodetect_deploy_interfaces = ramdisk,bootc,direct
enabled_deploy_interfaces = autodetect,direct,fake,ramdisk,custom-agent,bootc

05

베어메탈 이미지 프로비저닝 세 가지

세 시나리오는 모두 같은 서버에 OS를 설치하지만, 이미지가 포장되고 이동하는 경로가 다릅니다. 아래 표에서 “무엇을 빌드해야 하는가”, “어디를 거치는가”, “어느 릴리스에서 지원되는가”를 한 번에 비교할 수 있습니다.

비교 항목현재 방식OCI 아티팩트bootc 이미지
빌드 필요물 컨테이너 베이스 이미지의 마지막 레이어에 os-image.qcow2와 copy-out 스크립트를 넣습니다. bootc를 쓰려면 먼저 qcow2로 변환해야 합니다. qcow2를 만들고 ORAS로 매니페스트 + qcow2 아티팩트를 업로드합니다. bootc도 먼저 qcow2로 변환해야 합니다. 평범한 bootc 컨테이너 이미지만 빌드합니다. qcow2 생성과 변환이 모두 필요 없습니다.
배포 경로 레지스트리 → provision server → qcow2 HTTP 다운로드 → IPA → 디스크 레지스트리 → Metal3 Ironic → qcow2 추출·전달 → IPA → 디스크 레지스트리 → IPA가 bootc 이미지 직접 다운로드 → bootc가 디스크에 설치

장단점 익숙하고 호환성이 높지만 빌드·배포 경로가 길고, qcow2와 provision server가 필요합니다. 운영 중 드리프트와 롤백 문제도 남습니다. provision server를 없애 경로를 줄입니다. 그러나 qcow2를 계속 만들고, qcow2가 가진 빌드·운영 문제도 그대로입니다. 앱과 같은 도구·레지스트리·태그를 사용하고 원자적 업데이트와 읽기 전용 /usr를 얻습니다. qcow2를 만들거나 배포할 필요가 없습니다.

발표의 지원 릴리스와 “지원 목표” 표기는 슬라이드가 제시한 시점의 상태입니다. 실제 제품 적용 전에는 해당 배포판과 Metal3 릴리스의 현재 문서를 확인해야 합니다.

시나리오 1 · 현재 방식

패키징

컨테이너 안에 qcow2를 넣는다

평범한 컨테이너 베이스 이미지에 os-image.qcow2를 마지막 레이어로 추가합니다. 이미지가 스스로 압축을 풀도록 copy-out 스크립트도 함께 넣습니다. openstack-baremetal-operator의 httpd가 시작될 때 init 컨테이너가 이 스크립트를 실행합니다.

남는 문제

bootc도 다시 qcow2가 된다

bootc OS를 배포하고 싶어도 먼저 qcow2로 변환해야 합니다. 컨테이너 레지스트리는 포장 상자일 뿐, 실제 설치 경로는 여전히 디스크 파일 중심입니다.

  1. 01 · 저장컨테이너 레지스트리qcow2가 들어 있는 컨테이너 이미지를 보관한다.
  2. 02 · 중간 단계provision server이미지를 내려받고 qcow2를 HTTP로 내보낸다.
  3. 03 · 전달IPAqcow2 파일을 HTTP로 다운로드한다.
  4. 04 · 설치베어메탈 디스크IPA가 이미지 내용을 디스크에 쓴다.

경로가 길고 provision server가 중간에 반드시 들어갑니다.

시나리오 2 · OCI 아티팩트

패키징

매니페스트와 qcow2만 저장한다

OCI 아티팩트는 매니페스트와 qcow2 아티팩트로 구성됩니다. 구조가 단순하고 컨테이너 이미지와 같은 레지스트리 인프라를 이용합니다. Metal3 OCP-4.20에서 지원됩니다.

남는 문제

qcow2는 여전히 필요하다

provision server는 사라지지만 qcow2를 빌드하는 단계는 남습니다. bootc를 배포하려면 여전히 먼저 qcow2로 바꿔야 하므로 이미지 빌드와 서버 상태 관리 문제까지 해결하지는 못합니다.

  1. 01 · 저장컨테이너 레지스트리매니페스트와 qcow2 아티팩트를 보관한다.
  2. 02 · 직접 접근Metal3 Ironic레지스트리에서 아티팩트를 직접 가져온다.
  3. 03 · 변환qcow2 추출아티팩트를 디스크 이미지로 꺼낸다.
  4. 04 · 설치IPA → 디스크추출한 qcow2를 서버 디스크에 쓴다.

중간의 provision server가 그림에서 사라져 배포 경로가 짧아집니다.

시나리오 3 · bootc 이미지

가장 큰 변화

그냥 평범한 bootc 컨테이너 이미지를 사용합니다. Metal3 OCP-4.23 지원 목표이며 RHOSO-19의 권장 옵션입니다. qcow2를 만들 필요도, qcow2를 HTTP로 배포할 필요도 없습니다.

  1. 01 · 선언BareMetalHost커스텀 리소스에 bootc 이미지 태그를 적는다.
  2. 02 · 선택Metal3 Ironic이미지 URL을 보고 bootc deploy를 고른다.
  3. 03 · 직접 다운로드IPA → 레지스트리베어메탈 노드가 bootc 이미지를 직접 가져온다.
  4. 04 · 설치bootc → 디스크bootc가 OS를 실제 디스크에 설치한다.

범례에서 “qcow2 HTTP 다운로드” 화살표가 완전히 사라지는 이유가 여기에 있습니다.

구성요소 지도와 데모 흐름

발표의 데모는 쿠버네티스 커스텀 리소스를 만드는 데서 시작해 호스트가 실제로 부팅하는 지점까지 이어집니다. 관리자는 “어떤 서버를 어떤 이미지로 만들 것인가”를 선언하고, 각 컨트롤러와 에이전트가 그 선언을 실제 작업으로 바꿉니다.

컨테이너 이미지 레지스트리

bootc 이미지의 태그와 레이어를 보관합니다. bootc 경로에서는 IPA가 이 레지스트리에서 직접 이미지를 가져옵니다.

오케스트레이션 컨테이너 이미지 태그 컨테이너 이미지 다운로드 qcow2 HTTP 다운로드

데모: 커스텀 리소스에서 호스트 배포까지

  1. 01 · 작성커스텀 리소스 생성OpenStackBaremetalSet과 BareMetalHost를 쿠버네티스에 제출한다.
  2. 02 · 지정bootc 이미지 태그 연결호스트 리소스가 레지스트리의 bootc 이미지를 가리킨다.
  3. 03 · 조정Metal3 Ironic autodetect이미지 종류를 판단하고 bootc deploy를 선택한다.
  4. 04 · 설치IPA가 OS를 배포노드가 이미지를 직접 받아 디스크에 설치하고 부팅한다.
초보자를 위한 한 문장

커스텀 리소스는 “서버를 이 상태로 만들어 주세요”라고 적은 주문서입니다. 컨트롤러는 주문서를 읽고 Ironic에 일을 시킵니다. IPA는 현장에서 실제 디스크 작업을 하는 설치 기사입니다.

07

용어 빠른 사전

본문을 읽다가 막히는 이름을 다시 확인하는 표입니다. 처음 접하는 독자는 “완성된 디스크 파일”, “앱스토어 같은 저장소”, “실제 서버 설치 기사”라는 세 가지 비유를 기억하면 됩니다.

용어초보자용 뜻
qcow2QEMU Copy On Write version 2. 완성된 하드디스크를 통째로 복사한 것처럼 쓰는 디스크 이미지 파일입니다.
OCIOpen Container Initiative. 컨테이너 이미지 형식과 런타임을 위한 개방형·벤더 중립 표준입니다.
bootc이미지 모드 리눅스 도구입니다. 커널과 부트로더까지 포함한 OS 전체를 OCI 컨테이너 이미지처럼 관리하고 설치합니다.
IronicOpenStack의 베어메탈 프로비저닝 서비스입니다. 실제 서버 디스크에 이미지를 쓰고 상태를 관리합니다.
Metal3“metal cubed”로 읽는 CNCF 프로젝트입니다. 쿠버네티스 리소스로 베어메탈 서버를 관리하고 내부에서 Ironic을 사용합니다.
BMaaSBare Metal as a Service. 가상 머신 대신 실제 서버를 클라우드 자원처럼 빌려주는 모델입니다.
OCPOpenShift Container Platform. Red Hat이 제공하는 쿠버네티스 컨테이너 플랫폼입니다.
RHOSORed Hat OpenStack Services on OpenShift. OpenShift 위에서 OpenStack 컨트롤 플레인을 운영하는 제품입니다.
IPAironic-python-agent. 프로비저닝 대상 베어메탈 노드에서 이미지를 다운로드하고 디스크에 설치하는 에이전트입니다.
CRDCustom Resource Definition. 쿠버네티스 API에 새로운 종류의 주문서 양식을 추가하는 정의입니다.
아티팩트배포나 빌드의 결과물입니다. OCI 아티팩트에서는 컨테이너가 아닌 qcow2 같은 임의의 파일을 뜻합니다.
레지스트리이미지를 보관하고 내려주는 저장소입니다. 앱스토어처럼 이름, 태그, 버전으로 결과물을 찾습니다.
매니페스트이미지의 구성 목록을 가리키는 JSON 목차입니다. 레이어와 컨피그의 위치·다이제스트를 기록합니다.
레이어이미지 파일시스템의 한 겹입니다. 여러 레이어를 합치면 컨테이너 또는 OS의 파일 트리가 됩니다.
부트로더 · grub/shim전원을 켠 뒤 커널을 찾아 시작하는 프로그램입니다. grub은 부팅 메뉴·로딩을 맡고 shim은 부트 체인의 보조 단계입니다.
systemd리눅스가 부팅된 뒤 서비스와 프로세스를 시작·감독하는 시스템 관리자입니다.
provision server현재 방식에서 컨테이너 안의 qcow2를 꺼내 HTTP로 내보내는 중간 서버입니다. bootc 경로에서는 이 중간 단계가 필요 없습니다.
autodetect이미지 URL과 내용이 qcow2인지 bootc인지 판단해 Ironic deploy 인터페이스를 자동 선택하는 기능입니다.
컨테이너 이미지프로그램과 실행에 필요한 파일을 묶어 저장한 패키지입니다. bootc에서는 이 패키지가 OS 전체가 됩니다.
원자적 업데이트·롤백업데이트를 중간 상태로 노출하지 않고 한 번에 전환하는 방식과, 문제가 생기면 이전 이미지 상태로 돌아가는 기능입니다.

08

마무리 · 중간 단계를 하나씩 없애기

한 문장 결론
운영체제를 디스크 파일이 아니라 버전이 붙은 컨테이너 이미지로 다루면, 빌드·배포·운영의 언어가 하나로 이어집니다.

현재 방식에서 OCI 아티팩트로 가면 provision server가 사라집니다. bootc로 가면 qcow2 자체가 사라집니다. Ironic의 autodetect는 이 세 경로를 이미지 종류에 맞춰 연결합니다.

기억할 것 01

bootc는 앱 컨테이너가 아니다

겉으로는 OCI 이미지지만 안에는 커널·systemd·부트로더를 포함한 부팅 가능한 OS가 있습니다. 그래서 베어메탈과 VM에 설치할 수 있습니다.

기억할 것 02

OCI 아티팩트와 구분하기

OCI 아티팩트는 qcow2를 레지스트리에 저장하는 방법입니다. 배포 경로는 짧게 하지만 qcow2를 만드는 문제까지 없애지는 않습니다.

기억할 것 03

태그만으로 운영이 끝나지는 않는다

이미지 태그·다이제스트, 레지스트리 접근 권한, 하드웨어 호환성, 릴리스 지원 상태를 함께 검증해야 합니다. 발표의 데모는 이 연결 고리를 보여 주는 출발점입니다.
