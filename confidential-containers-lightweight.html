1막 · 배경: 누구를 믿어야 할까?

사용 중인 데이터도 보호하기

문서를 금고에 보관하는 것은 저장 중 보호, 봉인된 봉투로 보내는 것은 전송 중 보호에 해당합니다. 하지만 계산하려면 문서를 꺼내 읽어야 합니다. 컨피덴셜 컴퓨팅(Confidential Computing, CC)은 바로 이 사용 중 데이터를 보호하는 기술입니다. 신뢰 실행 환경(Trusted Execution Environment, TEE)은 하드웨어가 경계를 지키는 작업실입니다. 워크로드(Workload)는 그 안에서 실행할 프로그램과 작업을 뜻합니다.

데이터 보호는 세 가지 상태로 나뉜다.

  • 저장 중 데이터(Data at Rest) → 스토리지 암호화
  • 전송 중 데이터(Data in Transit) → 네트워크 암호화
  • 사용 중 데이터(Data in Use) → 컨피덴셜 컴퓨팅. 여기가 그동안 비어 있던 칸이다.

TEE(Trusted Execution Environment, 신뢰 실행 환경)가 제공하는 세 가지 성질:

  • 격리(Isolation): TEE를 하위 소프트웨어, 관리자, 다른 클라우드 테넌트로부터 분리한다.
  • 암호화와 통제(Encryption and Control): 워크로드 소유자가 복호화 키를 쥔다. 클라우드 사업자도 못 본다.
  • 검증/어테스테이션(Verification/Attestation): 실행 환경의 진위를 증거로 확인하는 절차입니다. TEE가 진짜이고, 올바르게 설정됐고, 안에 돌아가는 소프트웨어가 기대한 그것임을 암호학적으로 증명한다.

대표 사용 사례

데이터 클린룸(Data Clean Room)은 여러 참여자가 원자료를 서로 공개하지 않고 공동 분석을 수행하는 환경입니다. 컴플라이언스(Compliance)는 조직이 따라야 할 규정과 요구사항을 준수한다는 뜻입니다. 보호된 작업실 안에서 민감한 부분만 계산하고 결과를 꺼내는 사용 사례를 떠올리면 됩니다.

  1. 데이터 클린룸에서의 다자간 분석 — 금융 사기 탐지, 헬스케어 연구, 애드테크
  2. 기밀성·컴플라이언스가 필요한 클라우드 마이그레이션 — 민감 워크로드 이전
  3. 고보안 프로세스/함수 — 키 관리, 결제 처리

신뢰 경계 비교

신뢰 경계(Trust Boundary)는 기밀 데이터를 보호하기 위해 누구까지 믿어야 하는지 나누는 선입니다. 가상 머신(Virtual Machine, VM)은 물리 컴퓨터 안에 소프트웨어로 만든 별도의 컴퓨터입니다. 실제 컴퓨터 쪽은 호스트(Host), VM 안쪽은 게스트(Guest)라고 부릅니다. 운영체제(Operating System, OS)는 프로그램과 하드웨어 자원을 관리하며, 커널(Kernel)은 그 핵심 부분입니다. 하이퍼바이저(Hypervisor)는 VM을 만들고 격리하는 기반 소프트웨어입니다. 펌웨어(Firmware)와 그 부팅용 형태인 BIOS는 OS가 시작하기 전 기계를 준비합니다. Intel TDX(Trust Domain Extensions)는 VM 단위, Intel SGX(Software Guard Extensions)는 앱의 보호 영역인 엔클레이브(Enclave) 단위로 격리합니다. 아래 그림은 소프트웨어 관점의 경계를 비교합니다. 하드웨어 보호 기반까지 믿을 필요가 없어진다는 뜻은 아닙니다.

  • CC 없음: 클라우드 스택/관리자, BIOS/펌웨어, 호스트 OS/하이퍼바이저, VM 게스트 관리자, 게스트 OS, 앱 전부가 기밀 데이터에 접근 가능한 신뢰 경계 안에 들어온다.
  • Intel TDX(VM 격리): 게스트 OS와 애플리케이션만 신뢰 경계 안. 클라우드 스택·펌웨어·하이퍼바이저·VM 관리자가 밖으로 빠진다.
  • Intel SGX(앱 격리): 엔클레이브 안의 앱만 신뢰 경계 안. 게스트 OS까지 밖으로 빠져 가장 좁다.

Intel TDX

클라우드 서비스 제공자(Cloud Service Provider, CSP)는 컴퓨터 자원을 빌려주는 사업자입니다. TDX의 보호 단위인 신뢰 도메인(Trust Domain, TD)마다 서로 다른 메모리 암호화 키를 씁니다. 임대 건물의 관리자가 열 수 없는 작업실을 만드는 비유입니다. 작업실 안에 큰 사무실을 꾸밀지, 필요한 책상만 놓을지는 별개의 선택입니다.

  • 하드웨어로 강제되는 VM 격리. Trust Domain(TD) 단위로 메모리를 각기 다른 키로 암호화한다(TD Key 1, TD Key 2).
  • CSP의 호스트 OS·하이퍼바이저·펌웨어·BIOS와 시스템 관리자는 신뢰 경계 밖. 데이터가 보이지 않는다.
  • 게스트 OS는 "경량 또는 풀"로 선택 가능 — 이 발표의 핵심 실마리.

컨피덴셜 컴퓨팅 + 컨테이너: 배포 옵션 스펙트럼

컨테이너(Container)는 프로그램과 실행에 필요한 파일을 묶어 실행하는 단위입니다. 이미지(Image)는 그 실행 환경을 배포하기 위한 파일 묶음입니다. 쿠버네티스(Kubernetes, K8s)는 컨테이너의 배치와 실행을 관리하고, 파드(Pod)는 함께 실행할 컨테이너 한 개 또는 몇 개를 묶는 최소 실행 단위입니다. 런타임(Runtime)은 이 컨테이너를 실제로 실행하는 소프트웨어입니다. 라이브러리 OS(Library OS, LibOS)는 앱에 필요한 OS 기능을 라이브러리 형태로 제공하는 방식입니다. 컨피덴셜 VM(Confidential VM, CVM)은 TEE로 보호되는 VM입니다. 아래의 공격 표면(Attack Surface)은 공격자가 노려볼 수 있는 코드와 인터페이스의 범위입니다. 범용 기능을 늘리면 유연성도 늘지만, 경계 안에 들여오는 코드도 많아집니다. SDK(Software Development Kit)는 앱 개발에 쓰는 도구 묶음입니다. 아래의 Gramine·Occlum은 LibOS의 예이고, 나머지 제품·서비스 이름은 발표가 각 배포 형태에 배치한 예시입니다.

신뢰 경계 안에 들어가는 소프트웨어 양이 적은 것부터 많은 것 순으로 A~E:

  • A. 목적 특화 SGX 어플라이언스/앱 (Intel SGX SDK) — 이 배포 스펙트럼에서 공격 표면 최소
  • B. 전형적 SGX 앱/서비스: 컨테이너 + 라이브러리 OS (Gramine, Occlum, AKS for SGX, Edgeless Marblerun)
  • C. TDX 하드웨어 격리 컨피덴셜 컨테이너: 단순화된 커널 + 컨테이너 관리 시스템 (CoCo, Gramine TDX, Edgeless Contrast, Google Confidential Space)
  • D. 전형적 TDX 컨피덴셜 VM: 풀 게스트 OS (SUSE, Ubuntu, RHEL, Azure CVM)
  • E. 컨피덴셜 클러스터를 담은 TDX 격리 VM: 풀 게스트 OS + 컨테이너 관리 시스템 (Edgeless Constellation, AKS, GKE) — 이 배포 스펙트럼에서 공격 표면 최대, 유연성 최대

RunC → Kata → CoCo

RunC(runc)는 리눅스의 격리 기능을 사용하는 컨테이너 런타임입니다. 네임스페이스(Namespace)는 프로세스가 보는 자원 목록을 분리하는 기능으로, 같은 건물의 방마다 다른 주소록을 주는 것과 비슷합니다. Seccomp는 커널 호출을 제한하고, MAC(Mandatory Access Control)은 강제 접근 정책을 적용하며, CAPS(Capabilities)는 관리자 권한을 잘게 나눠 제한합니다. Kata Containers는 Pod마다 VM을 두는 런타임입니다. Confidential Containers(CoCo)는 여기에 사용 중 데이터 보호를 결합하는 프로젝트입니다. 신뢰 컴퓨팅 기반(Trusted Computing Base, TCB)은 보안을 위해 반드시 신뢰해야 하는 요소의 집합입니다. 방을 나누는 것, 별도 건물을 두는 것, 건물 소유자도 내부를 볼 수 없게 하는 것의 차이를 읽어 보세요.

  • Traditional RunC: 리눅스 네임스페이스로 격리. 모든 컨테이너가 호스트 리눅스 커널을 공유한다. Seccomp/MAC/CAPS 필터로 방어.
  • Kata Containers: 하드웨어 가상화로 격리. Pod마다 자기 게스트 리눅스 커널을 가진다. 호스트 커널 공유가 끊겨 CSP를 보호한다.
  • Confidential Container(CoCo): 워크로드가 암호화된 메모리에서 실행된다. CSP 자체가 TCB(신뢰 컴퓨팅 기반)에서 빠진다.

TDX CoCo 위협 모델

위협 모델(Threat Model)은 무엇을 보호하고 누구를 신뢰하지 않을지 정한 설계 전제입니다. PodVM은 Pod 하나를 담는 CVM이며, Pod-as-a-CVM은 이 대응 관계를 뜻합니다. 아래 그림에서 비신뢰 요소도 실행과 저장을 돕지만, 데이터의 기밀성과 무결성을 그 요소의 선의에 맡기지 않습니다. 무결성(Integrity)은 데이터가 허락 없이 바뀌지 않았다는 성질입니다.

VMM(Virtual Machine Monitor)은 VM의 실행과 가상 장치를 관리하는 사용자 공간 소프트웨어입니다. KVM(Kernel-based Virtual Machine)은 리눅스 커널의 가상화 기능입니다. 루트 파일 시스템(Root File System, rootfs)은 게스트의 기본 파일·디렉터리 전체입니다. TD-Shim / TDVF(TDX Virtual Firmware)는 TDX 게스트를 부팅시키는 가상 펌웨어로, 뒤에서 크기와 기능을 비교합니다. 게스트 내부 이미지 풀(In-Guest Image Pull)은 프로그램 이미지 파일을 보호된 VM 안에서 직접 가져오는 방식입니다. 레지스트리(Registry)는 이미지를 보관·배포하는 저장소입니다.

게스트 안에서 일하는 담당자

kata-agent는 컨테이너의 생성·실행·종료를 관리합니다. image-rs는 이미지 준비, ocicrypt-rs는 암호화 이미지 처리, Confidential DataHub(CDH)는 기밀 데이터 접근을 맡는 구성 요소입니다. Attestation Agent(AA)는 검증 증거를 준비하고, KBC(Key Broker Client)는 키 중개 서비스와 통신합니다. DCAP Lib(Data Center Attestation Primitives Library)는 하드웨어 검증에 쓰이는 라이브러리입니다.

밖에서 증거를 확인하는 담당자

KBS(Key Broker Service)는 검증 결과와 정책에 따라 키를 중개하고, AS(Attestation Service)는 증거를 검증합니다. RVPS(Reference Value Provider Service)는 비교할 기준값을 제공하며, KMS(Key Management Service)는 키를 관리합니다. DCAP QGS(Quote Generation Service)는 검증용 증거 생성을 돕지만 그림에서는 비신뢰 측입니다.

컨트롤 플레인(Control Plane)은 쿠버네티스의 관리 영역으로, etcd는 상태 저장소, API server는 요청 창구, 스케줄러는 배치 담당, 컨트롤러 매니저는 원하는 상태를 유지하는 담당자입니다. kubelet은 각 노드의 실행 담당자이고, containerd/CRI-O는 컨테이너 실행을 중개합니다. kata-shim은 호스트에서 Kata 실행을 연결하는 구성 요소입니다. Runtime Validator는 실행 요청을 정책에 맞춰 검사하며, OPA(Open Policy Agent)는 그 정책 판단 엔진입니다. 측정 부팅(Measured Boot)은 부팅한 코드의 측정값을 기록해 이후 검증에 쓰는 방식입니다. 데이터 볼륨(Data Volume)은 앱의 데이터를 담는 별도 저장 공간입니다.

Pod 단위 TCB 안에 들어가는 것과 밖에 있는 것이 나뉜다.

  • 신뢰: PodVM 내부 — kata-agent, image-rs, ocicrypt-rs, Confidential DataHub, Attestation Agent, KBC, DCAP Lib, 게스트 커널/rootfs, TD-shim/TDVF, 컨테이너 이미지와 데이터 볼륨
  • 신뢰: 원격 어테스테이션 측 — CoCo KBS(Key Broker Service), CoCo AS(Attestation Service), RVPS, KMS
  • 비신뢰: K8s 컨트롤 플레인(etcd, API server, kubelet, 스케줄러, 컨트롤러 매니저), containerd/CRI-O, kata-shim, VMM(Cloud Hypervisor/QEMU/Dragonball), 호스트 커널/KVM, 이미지 레지스트리, 스토리지, DCAP QGS
  • 게스트 내부 이미지 풀(in-guest image pull), 이미지 검증/복호화, Runtime Validator + OPA 정책, Measured Boot가 신뢰 경로를 구성한다.

2막 · 문제 진단: 작은 작업에 큰 준비 비용

더 가볍고 빠른 CoCo가 필요한 사용 사례

서버리스(Serverless)는 사용자가 서버 관리보다 함수나 요청 처리에 집중하는 실행 방식입니다. 엣지(Edge)는 데이터가 생기는 현장 가까이에서 계산하는 배치입니다. 에이전트 샌드박스(Agent Sandbox)는 AI가 도구를 실행할 때 영향을 가두는 환경입니다. 짧게 일할 작업을 위해 매번 큰 사무실을 여는 비용이 특히 아깝습니다. 콜드 스타트(Cold Start)는 준비되지 않은 상태에서 요청을 받아 실제 실행이 시작되기까지의 과정과 지연입니다. 아티팩트(Artifact)는 배포할 이미지나 빌드 결과물을 뜻합니다. 서버리스 그림의 Function은 실행 함수, Event Bridge는 이벤트 전달 창구, API Gateway는 외부 요청 입구, Application Engine은 앱 실행 기반입니다. IDaaS는 인증 서비스, MQ는 메시지 큐, BaaS는 백엔드 서비스입니다.

  1. 컨피덴셜 서버리스 — Function, Event Bridge, API Gateway, Application Engine, IDaaS/MQ/BaaS 연동
  2. 컨피덴셜 엣지 배포 — 실시간 데이터 처리, 데이터 캐싱, 로컬 추론을 엣지 노드/서버에서
  3. 컨피덴셜 에이전트 샌드박스 — AI 에이전트가 도구를 호출하는 격리 환경

핵심 지표: 콜드 스타트 지연 시간, 기본 메모리 사용량, 아티팩트/이미지 크기

TDX CoCo 콜드 스타트 경로

호스트 컨트롤 패스(Host Control Path)는 실행 요청이 호스트의 관리 구성 요소를 통과하는 경로입니다. 이미지 준비(Image Preparation)는 프로그램 파일을 가져와 풀고 실행 가능한 파일 시스템으로 연결하는 과정입니다. 요청 버튼을 누른 시점과 앱이 일하기 시작한 시점 사이에는 다음과 같은 준비가 끼어 있습니다.

호스트 컨트롤 패스 → PodVM 부팅 → 이미지 준비(image preparation) 순으로 시간이 쌓인다.

콜드 스타트 시간은 어디로 가는가

Early Linux는 게스트 리눅스 부팅의 초기 구간입니다. VMM(Virtual Machine Monitor)은 하이퍼바이저의 사용자 공간 부분으로, VM 장치와 실행을 관리합니다. 그림의 막대는 비용이 어느 구간에 몰리는지를 보여 줍니다. 발표 자료에 없는 절대 시간이나 비율을 이 그림에서 계산하지 않습니다.

측정 결과 구간별 기여도:

  • PodVM 부팅: 콜드 스타트의 지배적 구성 요소이며, 용량(메모리 크기)이 커질수록 가장 크게 늘어나는 부분
  • Early Linux: PodVM 부팅 안에서도 용량에 따라 가장 크게 증가하는 구간
  • 이미지 준비: 게스트 내부 이미지 풀/언팩. 부팅 이후에 붙는 이미지 의존적 비용
  • 호스트 컨트롤 패스: 쿠버네티스 요청 → Kata 런타임/shim → 샌드박스 준비. 기여도는 작고 거의 고정

구간 순서: 호스트 컨트롤 패스 → VMM 설정 → 펌웨어 → Early Linux → 게스트 서비스 → 이미지 준비. 메모리가 작은 경우와 큰 경우를 비교하면 Early Linux 구간이 특히 벌어진다.

PodVM 메모리는 어디로 가는가

기본 비용(Baseline)은 앱이 일을 거의 하지 않아도 환경을 유지하는 데 드는 자원입니다. 상주 워킹셋(Resident Working Set)은 실제 메모리에 올라와 쓰이는 부분입니다. 집적도(Density)는 같은 장비에 얼마나 많은 작업을 담을 수 있는지를 뜻합니다. 사무실을 크게 예약했다고 직원이 곧바로 늘지는 않지만, 개장 준비는 더 오래 걸리는 상황과 닮았습니다. 레지스트리(Registry)는 이미지를 보관·배포하는 저장소이고, 언팩(Unpack)은 묶인 파일을 풀어 놓는 과정입니다. 캐시(Cache)는 재사용용 저장, 스테이징(Staging)은 처리 중 임시 보관입니다.

세 가지 축으로 분해된다.

  • Pod당 기본 비용(Per-Pod baseline): PodVM 메모리 = 애플리케이션 메모리 + CoCo 서비스 + 게스트 커널 + VM 시스템 상태. PodVM 오버헤드가 워크로드 메모리를 압도해서 집적도(density)가 떨어진다.
  • 설정된 메모리(Configured memory): PodVM을 크게 잡아도 실제 상주 워킹셋은 비슷하다. 큰 설정 메모리는 워크로드 실행 전 초기화 시간만 길게 만든다.
  • 이미지 준비: 레지스트리 → PodVM으로 다운로드/언팩/캐시·스테이징하며 추가 메모리를 쓴다. 이미지에 따라 비용이 달라진다.

CoCo의 Pod당 비용 정리

루트 파일 시스템(Root File System, rootfs)은 게스트가 기본 경로에서 보는 파일과 디렉터리 전체입니다. 데몬(Daemon)은 뒤에서 계속 일하는 서비스 프로그램입니다. 페이지 수용(Page Acceptance)은 게스트가 보호 메모리 페이지를 사용 가능한 것으로 받아들이는 절차입니다. 여기서 sub-200ms, 즉 200ms 미만은 통상적 마이크로VM의 기동 목표이지, 이 발표가 CoCo에서 달성했다고 보고한 결과가 아닙니다. 마이크로VM(MicroVM)은 장치와 기능을 줄인 작은 VM입니다.

세 가지 "세금"이 붙는다.

  1. 범용 PodVM 세금: Pod마다 풀 리눅스 부팅과 CVM 초기화. 범용 VMM, 가상 펌웨어, 게스트 리눅스 커널, rootfs가 통째로 복제된다.
  2. 게스트 측 CoCo 서비스 플레인 세금: Kata Agent와 CoCo 게스트 데몬들, 게스트 측 이미지 준비와 워크로드 셋업.
  3. CC 고유의 증폭: TDX 보호 메모리, VM 수준 측정/어테스테이션, 워크로드 시작 전 보안 초기화 비용. 그 결과 통상적인 마이크로VM 기동 목표(200ms 미만)에 도달하기 어렵다. 이유는 (a) 호스트 측 직접 커널 로딩이 금지되고 (b) TDX 프라이빗 메모리 설정과 필요한 페이지 수용(page acceptance) 과정이 필요하기 때문.

한 줄 결론: 전체 PodVM 상태가 Pod마다 복제되며, Pod 간에 상각(amortization)되지 않는다.

3막 · 경량화 방법: 각 층에서 덜어내기

전체 그림

경량화(Lightweight)는 실제 작업에 불필요한 구성 요소와 그 비용을 덜어내는 접근입니다. initrd(Initial RAM Disk)는 초기 부팅에 사용하는 메모리 기반 파일 묶음입니다. KVM(Kernel-based Virtual Machine)은 리눅스 커널의 가상화 기능입니다. CRI(Container Runtime Interface)는 쿠버네티스가 런타임에 요청하는 인터페이스이고, OCI(Open Container Initiative)는 컨테이너 이미지와 실행 형식을 정하는 표준 활동입니다. 스냅샷터(Snapshotter)는 이미지의 파일 시스템을 실행용으로 준비·관리하는 구성 요소입니다. 아래 층을 하나씩 줄이되 보호 경로가 이어져야 합니다.

아래에서 위로 쌓이는 스택에서 각 층을 경량화한다.

  • 하드웨어 + BIOS + TDX 모듈 + 호스트 커널/KVM (기반)
  • 경량 VMM
  • 경량 가상 펌웨어
  • 축소된 게스트 커널
  • 커스터마이즈된 게스트 rootfs / initrd
  • 호스트 기반 이미지 풀(host-based image pull) — snapshotter, CRI(containerd, CRI-O), OCI(kata runtime/shim v2)와 연결
  • 맨 위에 CoCo 앱

경량 VMM

풋프린트(Footprint)는 구성 요소가 차지하는 메모리 같은 자원 규모입니다. MiB는 메모리 용량을 나타내는 단위입니다. 라이브 마이그레이션(Live Migration)은 실행 중인 VM을 다른 호스트로 옮기는 기능이고, VFIO는 장치를 VM 등에 직접 연결하는 데 쓰이는 리눅스 인터페이스입니다. ACPI(Advanced Configuration and Power Interface)는 OS에 장치·전원 정보를 전달하는 규약이며, PCI(Peripheral Component Interconnect)는 장치 연결 규격입니다. 경량 후보 목록이 곧 모든 후보의 TDX 지원 보장을 뜻하지는 않습니다.

  • 후보: Dragonball, Cloud Hypervisor, Firecracker. 수십 MiB 수준의 베이스라인 풋프린트.
  • 바꿀 수 있는 것: 호스트 측 베이스라인, 즉 VMM 구현과 풋프린트. 대신 운영·호환성 트레이드오프가 생긴다(라이브 마이그레이션, VFIO, ACPI, PCI 등 기능 취사선택).
  • 없앨 수 없는 것: 풀 PodVM 비용 자체. Pod마다 범용 리눅스와 게스트 서비스가 여전히 돌고, Early Linux가 용량 관련 부팅 시간 증가의 대부분을 차지한다.
  • 갭: 모든 VMM이 CVM을 지원하지는 않으며, 지원해도 기능이 제한적이다.

경량 가상 펌웨어

TD-Shim과 TDVF(TDX Virtual Firmware)는 TDX 게스트의 부팅을 준비하는 가상 펌웨어입니다. 전자는 작은 부팅 안내원, 후자는 여러 설비를 갖춘 안내 데스크에 가깝습니다. UEFI(Unified Extensible Firmware Interface)는 펌웨어와 OS 사이의 표준 인터페이스입니다. Service TD는 보안 서비스 같은 특정 기능을 맡는 TD입니다. 아래 K/M은 원본의 크기 표기를 유지합니다.

표의 약어 읽기

Rust / C / ASM(Assembly)은 구현 언어이며, no-std는 Rust 표준 라이브러리 없이 구성한다는 뜻입니다. UEFI RT(Runtime Services)는 부팅 이후에도 제공되는 펌웨어 서비스입니다. ACPI ASL(ACPI Source Language)은 장치 정보를 기술하는 언어입니다. Virtio는 VM용 가상 장치 인터페이스입니다.

MADT(Multiple APIC Description Table)는 인터럽트 컨트롤러 정보를, DSDT(Differentiated System Description Table)는 장치 구성을 설명하는 ACPI 테이블입니다. IRQ(Interrupt Request)는 장치가 처리를 요청하는 신호이고, E820은 메모리 영역 정보를 전달하는 테이블 형식입니다. RTMR(Runtime Measurement Register)는 런타임 측정값을 담는 레지스터이며, EventLog는 측정 사건 기록입니다.

신뢰 부팅(Trusted Boot)은 측정값을 남겨 부팅 내용을 검증할 수 있게 하는 방식이고, 보안 부팅(Secure Boot)은 허용된 코드인지 확인하며 부팅하는 방식입니다. TD HOB(Hand-Off Block)는 부팅 단계에 전달하는 정보 묶음이고, TD-Payload는 실제로 올릴 OS 등의 실행 내용입니다. GRUB은 OS 커널을 올리는 부트 로더입니다.

축소된 게스트 커널

트레이스(Trace)는 실행 중 실제로 사용한 기능을 기록한 자료이며, 시스템 콜(System Call)은 앱이 커널에 요청하는 통로입니다. 필요한 방을 고르는 것이 전략이고, 나머지 방을 설계도에서 지우거나 출입을 막는 것이 메커니즘입니다. KCONFIG는 커널 빌드 기능을 선택하는 설정 체계입니다. 링커(Linker)는 컴파일된 코드를 합치는 도구이고, DCE(Dead Code Elimination)는 쓰이지 않는 코드를 제거하는 기법입니다. Seccomp-BPF는 BPF 프로그램으로 시스템 콜을 필터링하고, BPF-LSM은 리눅스 보안 훅에 BPF 정책을 연결합니다. 하드닝(Hardening)은 공격에 견디도록 설정과 구현을 강화하는 작업입니다.

전략(무엇을 줄일지)과 메커니즘(어떻게 줄일지)의 조합.

  • 전략: 트레이스 기반(워크로드 중심, 시스템 콜/커널 트레이스 활용), 하드웨어 중심(디바이스 인벤토리), 스펙 기반(전문가 지식/정적 분석)
  • 메커니즘: 설정 기반(KCONFIG, 매크로 삭제), 링커 수준 DCE(Dead Code Elimination — 더 세밀하지만 기본 지원이 없음), 런타임 공격 표면 정화(Seccomp-BPF, BPF-LSM)
  • CoCo의 갭: Kata에서 통하는 것이 CoCo에서 그대로 통하지 않는다. 공식 Kata 게스트 커널은 KCONFIG 프래그먼트로 마이크로VM에 최적화돼 있을 뿐, 최소화되어 있지도 CC를 위해 하드닝되어 있지도 않다. Kata의 Seccomp-BPF는 CC 전용 워크플로가 필요하고, BPF-LSM 구현은 CC 맥락에서 제대로 동작하지 않을 수 있다. 전략과 메커니즘 양쪽 모두 갭이 남아 있다.

이 절과 이후의 지원 공백은 발표가 진단한 시점의 상태입니다. 업스트림(Upstream)은 개별 실험 구현이 아니라 프로젝트의 공식 개발 본류를 뜻합니다.

커스터마이즈된 게스트 rootfs와 구성 요소

디스트로리스(Distroless)는 배포판의 범용 관리 도구를 빼고 앱 실행에 필요한 것만 담는 이미지 방식입니다. PID 1(Process ID 1)은 게스트에서 처음 실행되는 프로세스이며, init는 초기 서비스 시작과 관리를 맡습니다. 유저랜드(Userland)는 커널 바깥의 도구와 프로그램 모음입니다. 스트립(Strip)은 실행에 불필요한 심볼 정보를 제거하는 작업입니다. 도구함 전체를 들고 가는 대신 해당 작업에 필요한 공구만 챙기는 셈입니다.

  • Distroless 최소 의존성: 런타임에 실제로 필요한 바이너리, 라이브러리, 설정, 데이터만 남긴다.
  • 최소 부팅 스택: 풀 init 시스템 대신 작은 PID 1 / 초기 부팅 컴포넌트로 교체.
  • 범용 유저랜드 제거: 패키지 매니저, 리포지터리, 패키지 DB, 비필수 관리 도구 제외.
  • 얇은 이미지 구성: 재사용 가능한 코어는 베이스 이미지에, 선택적·버전별 기능은 별도 확장으로 분리.
  • 남긴 아티팩트는 스트립·압축: 심볼 제거, 가능한 곳은 바이너리·라이브러리 압축.
  • Kata 에이전트와 CoCo 게스트 컴포넌트(AA, CDH 등)를 분리(decouple).

CoCo 이미지 관리 문제

이미지 풀(Image Pull)은 레지스트리에서 이미지를 가져오는 일입니다. 레이어(Layer)는 이미지를 이루는 겹이고, 블롭(Blob)은 저장·전송되는 데이터 덩어리입니다. 다이제스트(Digest)는 내용을 해시로 요약한 지문이며, 메타데이터(Metadata)는 이미지의 구성과 속성을 설명하는 정보입니다. 마운트(Mount)는 파일 시스템을 사용할 경로에 연결하는 작업입니다. 호스트가 상자를 미리 풀어 공유하면 편하지만, 그 호스트를 믿지 않는 CoCo에는 검증 문제가 생깁니다.

  • 기존 방식: 이미지 레이어를 컨테이너 간에 공유하고 재사용한다. 호스트가 레지스트리에서 블롭을 받아 호스트 FS에 저장하고 컨테이너 rootfs로 변환한다.
  • CC 맥락의 문제: 이미지가 호스트/레지스트리 변조에 노출되고, 루트 파일 시스템이 호스트에 마운트된다.
  • 그래서 CoCo는 게스트 내부 이미지 풀을 택했다. 그 대가로 (a) 이미지 재사용 불가 (b) 콜드 스타트 지연 (c) 추가 메모리 오버헤드가 생긴다.

게스트 내부 이미지 풀: 원본 그림의 11단계

Relying Party는 어테스테이션 결과를 신뢰 결정에 사용하는 주체입니다. 아래 번호는 슬라이드 23의 화살표 번호를 따릅니다.

  1. PullImage: kubelet → containerd/CRI-O로 이미지 요청.
  2. PullImage: containerd/CRI-O → kata-shim으로 전달.
  3. PullImage: kata-shim → kata-agent로 전달.
  4. PullImage: 게스트 측에서 레지스트리로 이미지 요청.
  5. Download: 레지스트리에서 게스트 이미지 저장소로 다운로드.
  6. Image digest + metadata: 게스트 측에서 containerd/CRI-O로 이미지 지문과 메타데이터 반환.
  7. GetKey: KBS에 복호화 키 요청.
  8. GetAttestation: 어테스테이션 요청.
  9. SendAttestation: 검증 증거 전달.
  10. SendKey: 검증을 거쳐 키 전달.
  11. Decrypt → Unpack → Mount: 게스트 안에서 복호화하고 풀어 마운트.

호스트 풀 대안 #1: Syft + Blockfile + FS-verity Hook

CI(Continuous Integration)는 소프트웨어 변경을 자동으로 빌드·검사하는 과정입니다. SBOM(Software Bill of Materials)은 소프트웨어 구성 재료 명세이고, Syft는 이를 만드는 도구입니다. fs-verity는 파일 단위 무결성 검증 기능입니다. InitData는 시작할 환경에 묶어 전달하는 초기 정책 데이터입니다. Blockfile Snapshotter는 rootfs를 블록 이미지로 준비하는 구성 요소입니다. 훅(Hook)은 특정 실행 단계에 끼워 넣는 처리이고, prestart는 시작 직전 단계입니다. 납품 목록의 중요한 파일 지문부터 확인하는 접근입니다.

  • 구성: 오프라인 CI에서 Syft로 SBOM 기반 fs-verity 다이제스트 생성 → CoCo 템플릿 + InitData(신뢰 파일 정책) → 온라인 호스트에서 containerd + blockfile snapshotter로 rootfs 블록 이미지 생성 → CVM 기동 시 디바이스 부착 → 게스트에서 Kata prestart hook의 fs-verity 훅이 enable + measure + compare → BPF LSM(diglim-ebpf)이 exec/executable mmap 시점에 검사
  • 장점: 리눅스 fs-verity, Kata 게스트 훅, 이미지 스캐너를 재사용해 OCI 레이어 같은 침습적 변경 없이 선택 파일 무결성을 얻는다. 실행 파일·설정·정책 파일에 점진적 보호를 적용할 수 있다. 기존 SBOM 기반 파일 다이제스트 흐름을 그대로 쓰고, 이미지 빌더가 추가 아티팩트를 배포할 필요가 없다.
  • 함정: 정책 페이로드 한계 때문에 선택된 파일만 보호되고, 신뢰 파일 수가 늘수록 파일당 셋업 비용이 커진다. prestart 시점 검사만으로는 사용 시점 강제가 되지 않아 BPF LSM 같은 실행 정책이 별도로 필요하다.

enable → measure → compare는 검증 기능을 켜고, 지문을 측정하고, 정책의 지문과 비교하는 순서입니다. exec는 프로그램 실행, executable mmap은 실행 가능한 메모리 매핑입니다. diglim-ebpf는 그림에 제시된 BPF LSM 구현입니다. 시작 전에 출입증을 한 번 확인하는 것과 실제 문을 통과할 때마다 통제하는 것은 다릅니다.

호스트 풀 대안 #2: ComposeFS + FS-verity

ComposeFS는 공유 콘텐츠를 조합해 파일 시스템을 구성하는 기술입니다. EROFS(Enhanced Read-Only File System)는 읽기 전용 파일 시스템이며, OverlayFS는 여러 파일 시스템 층을 겹쳐 하나처럼 보이게 합니다. ORAS(OCI Registry As Storage)는 레지스트리로 아티팩트를 주고받는 도구입니다. genpolicy/initdata builder는 정책과 초기 데이터를 만드는 도구를 가리킵니다. 여러 주문이 같은 부품 창고를 쓰는 방식이라 공유에 유리하지만, 창고에서 들어오는 구조를 해석하는 게스트 코드도 살펴야 합니다.

  • 구성: 오프라인 CI의 composefs 툴체인 + genpolicy/initdata builder → ORAS/OCI 아티팩트 클라이언트로 OCI composefs 아티팩트 패키징·배포 → 온라인 호스트의 CRI-O/containers-storage에서 composefs 백엔드 스토리지 경로 → Kata 런타임이 CVM 기동 시 디바이스 부착 → 게스트에서 composefs 인식 rootfs 마운트(EROFS + overlayfs + fs-verity), kata-agent가 정책 강제, InitData 바인딩, TEE 측정 상태 연결
  • 장점: 공유 콘텐츠 스토어라서 중복 데이터가 없고 배포와 컨테이너 간에 페이지 캐시를 공유한다. 고정된 A/B 레이아웃 없이 유연한 rootfs 구성과 롤백이 가능하다.
  • 함정: 호스트가 통제하는 백킹 스토리지가 게스트 공격 표면에 남는다(커널 FS 코드는 익스플로잇에 충분히 견고하지 않다). 업스트림에 CRI→Kata 핸드오프나 메타데이터·오브젝트·씰(seal)을 위한 게스트 ComposeFS 마운트 경로가 없어 활성화 비용이 크다. 이미지 빌더가 추가 아티팩트를 배포해야 이득이 커진다.

페이지 캐시(Page Cache)는 파일 내용을 메모리에 보관해 재사용하는 기능입니다. A/B 레이아웃은 교체할 두 영역을 고정해 두는 구성이고, 롤백(Rollback)은 이전 상태로 되돌리는 일입니다. 핸드오프(Handoff)는 구성 요소 간 정보와 제어의 인계, 씰(Seal)은 내용의 검증에 연결되는 봉인 정보를 가리킵니다. 발표의 커널 파일 시스템 공격 표면 지적은 무결성 확인만으로 입력 해석 코드의 취약점까지 사라지지는 않는다는 뜻입니다.

호스트 풀 대안 #3: EROFS + DM-verity

dm-verity(Device Mapper Verity)는 파일 아래의 블록 단위에서 무결성을 검증하는 리눅스 기능입니다. 파서(Parser)는 저장된 구조를 읽어 해석하는 코드입니다. 이 방식은 블록을 검증한 뒤 EROFS 파서에 넘깁니다. 작은 부품마다 공유하는 대신 봉인한 상자, 즉 레이어 단위로 재사용하는 접근입니다.

  • 구성: 오프라인 CI의 독립 EROFS 빌더 + genpolicy/initdata builder → ORAS/OCI 클라이언트로 OCI EROFS + dm-verity 아티팩트 패키징·배포 → 온라인 호스트의 containerd + EROFS snapshotter → Kata 런타임이 CVM 기동 시 디바이스 부착 → 게스트에서 컨테이너 rootfs 마운트(EROFS + overlayfs + dm-verity), kata-agent 정책 강제, InitData 바인딩
  • 장점: 자기 완결적인 불변 EROFS 레이어. dm-verity가 검증된 블록만 게스트 EROFS 파서에 노출한다. 기존 Kata의 EROFS + dm-verity + OverlayFS 런타임 경로를 그대로 쓴다.
  • 함정: 콘텐츠 공유 입도가 거칠다(오브젝트 단위가 아니라 레이어 단위 재사용). 업스트림에 독립형 OCI→EROFS/dm-verity 빌더나 종단 간 아티팩트 임포트 경로가 없다. 이미지 빌더의 추가 아티팩트 배포에 의존한다.

특화 OS 커널을 언제 쓰나

특화(Specialization)는 실행할 작업에 맞춰 OS가 제공할 기능을 좁히는 설계입니다. 유니커널(Unikernel)은 앱에 필요한 OS 기능만 모아 작은 실행 이미지로 구성하는 특화 방식으로, 흔히 단일 주소 공간 구성을 사용합니다. 다만 다음 슬라이드의 Gramine-TDX는 앱과 LibOS의 권한 수준을 구분해 그립니다. 프로세스(Process)는 실행 중인 프로그램 단위이고, 마이크로서비스(Microservice)는 작은 기능으로 나눈 서비스입니다. vTPM(Virtual Trusted Platform Module)은 보안 키와 측정값을 다루는 TPM의 가상 형태입니다. LOC(Lines of Code)는 소스 코드 줄 수입니다. 다음 수치는 발표의 비교 규모이며 모든 리눅스·유니커널 구현의 공통 크기나 보안·속도 향상 배수를 뜻하지 않습니다.

  • 단일 프로세스 애플리케이션을 담은 경량 컨테이너: 마이크로서비스/함수, 에이전트 샌드박스
  • 강한 보안 요구가 있는 워크로드: Service TD(예: vTPM), 키 관리 서비스(KMS)
  • 규모 비교: 리눅스 기반 TD는 리눅스 커널만 약 500만 줄(~5M LOC), 유니커널 기반 TD는 약 5만 줄(~50K LOC). 코드 줄 수 기준 약 100배 차이.

CVM용 특화 OS 커널 구조

ring-3 / ring-0은 실행 권한 수준으로, 이 그림에서 각각 앱과 커널 영역을 구분합니다. 백엔드(Backend)는 공통 기능을 특정 실행 기반에 연결하는 구현입니다. vsock(Virtual Socket)은 게스트와 호스트 사이의 통신 통로이고, TCP/IP는 인터넷 통신 규약입니다. virtual FS는 가상 파일 시스템 연결, virtio-console은 가상 콘솔 장치입니다. vBIOS(Virtual BIOS)는 VM의 부팅 펌웨어 역할을 뜻합니다. Shared-FS 데몬은 호스트에서 파일 공유를 돕는 서비스입니다. 작은 게스트도 호스트와 통신하므로, 그 경계에 놓인 드라이버를 TDX에 맞게 강화해야 한다는 그림입니다.

  • 게스트 TD 안: 단일 프로세스 애플리케이션(guest ring-3) 아래에 백엔드 독립적인 LibOS(guest ring-0, 유니커널)가 있고, 그 아래 TDX 백엔드가 virtual sockets 드라이버, virtual FS 드라이버, virtio-console 등을 제공한다. TD-Shim이 vBIOS 역할.
  • 호스트 측: VMM(Cloud Hypervisor/QEMU/Firecracker)이 virtual sockets 디바이스와 virtual FS 디바이스를 제공하고, host ring-0의 리눅스 커널에서 KVM이 받친다. vsock-to-TCP/IP 브리지로 인터넷 연결, Shared-FS 데몬으로 파일 공유.
  • 파일 예: /usr/app(해시로 측정), /usr/conf.txt(암호화).
  • 근거 논문: Gramine-TDX: A Lightweight OS Kernel for Confidential VMs, ACM CCS'24. 저장소: Gramine-TDX 저장소

CoCo에서의 유니커널 지원

API(Application Programming Interface)는 프로그램 사이에서 요청·응답을 주고받는 약속입니다. Unikernel Agent는 기존 런타임 요청을 유니커널이 이해할 명령으로 바꾸는 중간 담당자입니다. gRPC는 프로그램 간 원격 호출 방식이고, I/O 다중화(Input/Output Multiplexing)는 여러 입출력 흐름을 나누어 처리하는 일입니다. 시크릿 프로비저닝(Secret Provisioning)은 검증된 환경에 키 등 비밀값을 전달하는 절차입니다. 일반 리눅스에 있던 기능을 모두 그대로 실행할 수 없으므로, 아래 네 갈래로 요청의 의미를 정리해야 합니다.

  • 스택: CRI(containerd, CRI-O) + snapshotter, OCI(kata runtime/shim v2) 아래에 Unikernel Agent를 두고, 유니커널 + TD-Shim + VMM(QEMU, CLH) 위에서 CoCo 앱을 실행한다.
  • Unikernel Agent가 하는 일: 프로토콜 변환(OCI/gRPC → 커스텀 TCP 명령), 인터페이스 모킹(no-op), 부팅 준비 상태 감지, I/O 다중화
  • 게스트 안의 In-Guest Control Routine: 소켓 서버, 명령 디스패처, 태스크 러너, 출력 포워더, 어테스테이션과 시크릿 프로비저닝

kata-agent API를 다루는 네 가지 방식

01 · 호스트 로컬 / 모킹

호스트에서 처리하거나 빈 동작으로 대응

모킹(Mocking)은 실제 기능 대신 대체 응답을 제공하는 것이며, no-op(No Operation)은 실질적인 작업을 하지 않는 응답입니다. 스텁(Stub)은 인터페이스를 맞추는 대체 구현입니다. 성공 응답만으로 기존 기능까지 제공되는 것은 아닙니다. TTY(Teletypewriter)는 프로세스의 터미널 입출력 인터페이스를 가리킵니다. cgroup(Control Group)은 프로세스 묶음의 자원 사용을 관리하는 리눅스 기능입니다. 핫플러그(Hotplug)는 실행 중 장치나 자원을 추가·제거하는 기능입니다.

  • 수명주기: createSandbox, createContainer
  • 프로세스·터미널(TTY): execProcess, winsizeProcess, writeProcessStdin
  • 자원 그룹(cgroup)·통계: updateContainer, statsContainer, getOOMEvent
  • 네트워크 설정: updateInterface, updateRoutes, listRoutes
  • 실행 중 장치 추가(Hotplug)·시스템: onlineCPUMem, memHotplugByProbe, addSwap, setGuestDateTime
02 · 하이브리드

VM 기동과 준비 확인을 결합

하이브리드(Hybrid)는 호스트 작업과 게스트 통신을 함께 쓰는 방식입니다. 핸드셰이크(Handshake)는 서로 준비 상태를 확인하는 통신입니다. startSandbox는 VM을 기동하고 핸드셰이크하는 경로입니다.

03 · 패스스루

게스트 제어 채널로 전달

패스스루(Passthrough)는 요청을 실제 처리 주체로 넘기는 방식입니다. startContainer와 signalProcess는 게스트 제어 채널을 통해 작업 시작과 프로세스 신호를 전달합니다.

04 · 기타 런타임

다른 OCI 호환 실행 경로

urunc처럼 유니커널을 다루는 OCI 호환 런타임을 이용하는 길도 있습니다. Kata의 API를 맞추는 경로 외의 선택지로 발표가 제시합니다.

TEE 재사용

웜 풀(Warm Pool)은 미리 준비해 둔 실행 환경의 묶음이고, 스냅샷(Snapshot)은 되돌아갈 수 있도록 저장한 상태입니다. 테넌트(Tenant)는 같은 기반을 사용하는 서로 다른 고객이나 작업 주체입니다. 중첩 어테스테이션(Nested Attestation)은 재사용 기반 위에 올린 작업 환경을 추가로 검증하는 단계입니다. 메모리 스크러빙(Memory Scrubbing)은 이전 작업의 잔여 데이터를 지우는 정화 작업입니다. 준비된 방을 다시 빌려주려면 앞선 손님의 자료가 남지 않아야 합니다.

콜드 스타트를 근본적으로 줄이는 다른 축: TEE 인스턴스를 웜 풀로 재사용한다.

  • 준비: 베이스 코드/런타임 로드 → 스냅샷
  • 테넌트 A 요청: 웜 풀 → 원격 어테스테이션 → 데이터/키 마운트 → 중첩 어테스테이션(nested attestation) → 실행 → 결과 내보내기
  • 리셋 트리거 → Clean → Rewind(스냅샷으로 되감기) → 메모리 정화/스크러빙
  • 테넌트 B 요청(재사용 경로): 데이터/키 마운트 → 중첩 어테스테이션 → 실행 → 결과 내보내기

재사용은 부팅할 코드의 양을 줄이는 것과 별도의 최적화 축입니다. 이전 고객의 상태를 제거하고 새 데이터·키와 검증을 연결하는 절차까지 포함해 보아야 합니다. 그림은 재사용 흐름을 제안하며, 모든 TEE에서 동일한 재사용이 곧바로 가능하다고 보장하지 않습니다.

05

핵심 메시지: 필요한 만큼만 신뢰하고, 필요한 만큼만 실행하기

  1. CoCo의 "호환성 우선" 설계는 훌륭한 출발점이지만, Pod마다 풀 PodVM을 복제하는 구조라 서버리스·엣지·에이전트 샌드박스에는 무겁다.
  2. 비용의 정체는 측정으로 특정된다. 콜드 스타트는 PodVM 부팅(특히 Early Linux)이, 메모리는 Pod당 기본 오버헤드가 지배한다. 게스트 내부 이미지 풀이 여기에 이미지 의존적 비용을 더한다.
  3. 1차 다이어트는 스택 각 층을 경량화하는 것이다. 경량 VMM, TD-Shim, 축소 게스트 커널, distroless rootfs, 그리고 무결성을 지키면서 호스트에서 이미지를 푸는 세 가지 대안.
  4. 단일 목적 워크로드에는 특화가 다음 단계다. 유니커널/LibOS 기반 특화 OS 커널은 발표의 비교에서 커널 코드 규모가 약 100분의 1이며, 공격 표면과 부팅 비용을 함께 낮추려는 접근이다.
  5. 남은 과제는 대부분 "업스트림 갭"이다. CVM을 지원하는 VMM의 제약, TD-Shim 호환성, CC 맥락에 맞는 커널 디블로팅과 BPF-LSM, 표준 아티팩트 빌더와 CRI-Kata 핸드오프 경로의 부재. 프로덕션에서 이런 특화 런타임을 관리·모니터링하는 문제도 열려 있다.
“One Size Fits None”이 던지는 질문

이 작업에 풀 리눅스와 모든 관리 기능이 필요한가? 무엇을 줄일 수 있고, 줄인 뒤에도 이미지·코드·키를 검증하는 경로가 이어지는가? 특화는 이 질문에 답하며 실행 환경을 설계하는 일입니다.
