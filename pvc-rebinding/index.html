먼저 알아둘 배경 지식

이 발표를 이해하려면 아래 개념이 필요하다. Kubernetes 스토리지를 처음 보는 사람 기준으로 정리한다.

  • Pod: 컨테이너가 실제로 실행되는 단위다. 언제든 죽고 다시 만들어질 수 있는 일회용 존재로 취급한다.
  • StatefulSet: 데이터베이스처럼 상태를 가진 앱을 굴리는 컨트롤러다. Pod마다 고정된 이름(예: db-0, db-1)과 전용 디스크를 붙여준다.
  • PersistentVolume (PV): 실제 디스크를 Kubernetes가 인식하는 객체로 표현한 것이다. 클러스터 전체에서 보이며, 어떤 드라이버로 어느 디스크를 쓰는지 적혀 있다.
  • PersistentVolumeClaim (PVC): "이만한 디스크가 필요하다"는 신청서다. 네임스페이스 안에 있으며, Pod는 PV를 직접 보지 않고 PVC를 통해 디스크를 쓴다.
  • StorageClass: 디스크를 어떤 방식으로 만들지 정한 템플릿이다. 어떤 드라이버(provisioner)를 쓸지, 디스크 등급은 무엇인지를 담는다.
  • 바인딩(binding): PVC 한 장과 PV 한 개가 짝이 되는 것이다. 짝이 지어지면 그 PVC를 쓰는 Pod가 해당 디스크를 마운트한다.
  • in-tree 드라이버: 예전에는 클라우드별 스토리지 코드가 Kubernetes 본체 안에 들어 있었다. 이것이 in-tree다. 유지보수가 어려워 2020년에 폐기 예정으로 지정됐다.
  • CSI (Container Storage Interface): 스토리지 드라이버를 Kubernetes 본체 밖에서 별도로 개발·배포하는 표준 방식이다. in-tree의 대체재다.
  • reclaim policy: PVC가 사라졌을 때 PV와 실제 디스크를 어떻게 할지 정한다. Delete면 디스크까지 지우고, Retain이면 디스크를 남긴다.
  • finalizer: 객체를 지우려 할 때 "아직 정리할 게 남았다"며 삭제를 붙잡아 두는 표식이다. 조건이 해소돼야 실제로 지워진다.
  • immutable 필드: 한 번 만들면 수정할 수 없는 항목이다. StorageClass의 provisioner, PV의 볼륨 소스가 여기에 해당해서 이 마이그레이션이 어려워진다.

이 발표의 핵심 아이디어를 한 문장으로

디스크는 그대로 두고, 그 디스크를 가리키는 Kubernetes 객체만 in-tree용에서 CSI용으로 갈아끼운다. Pod 재시작 시간 외에는 중단이 없다.

왜 "honeypot PV"라고 부르는가

새로 만든 CSI PV는 아직 존재하지 않는 PVC의 이름과 네임스페이스만 적어둔다. 나중에 StatefulSet이 같은 이름의 PVC를 만들면, 그 PVC가 이 PV를 발견하고 스스로 달라붙는다. 미리 놓아둔 덫에 걸리는 모양이라 honeypot이라고 부른다.

먼저, 창고에 비유해 봅시다

실제 Azure 디스크는 물건이 들어 있는 창고, PV는 창고의 주소와 출입 방식을 적은 시설 등록증, PVC는 사용자가 낸 창고 사용 신청서입니다. Pod는 그 창고를 쓰는 작업자이고, StatefulSet은 같은 이름의 작업자와 신청서가 다시 준비되도록 관리하는 담당자입니다. StorageClass는 새 창고를 마련할 때 쓰는 주문 양식입니다.

네임스페이스(namespace)는 한 클러스터 안에서 자원을 구분하는 작업 구역입니다. 클러스터(cluster)는 Kubernetes가 함께 관리하는 서버 묶음이고, 노드(node)는 그 안의 개별 서버입니다. PVC는 구역별 신청서이고, PV와 StorageClass는 클러스터 전체의 시설 목록과 주문 양식에 해당합니다. 컨트롤러(controller)는 실제 상태를 관찰하고 원하는 상태에 맞도록 객체를 생성·정리하는 자동 관리자입니다.

마운트(mount)는 디스크의 파일 시스템을 컨테이너가 파일 경로로 사용하도록 연결하는 일입니다. attach는 디스크를 노드에 연결하는 단계입니다. 둘은 연결 과정의 서로 다른 단계입니다.

이름이 같아도 같은 객체는 아닙니다

metadata.name은 사람이 읽는 이름이고, UID는 객체가 생성될 때 부여되는 고유 식별자입니다. 같은 이름으로 PVC를 다시 만들어도 UID는 바뀝니다. resourceVersion은 객체 변경 버전을 나타내는 값입니다. 이 차이가 뒤에서 설명할 재바인딩의 핵심입니다.

왜 이 규모에서 어려울까요?

RCM은 진료비 청구·수납 등 수익 주기를 관리하는 업무이고, 앰비언트 플랫폼은 진료 현장의 상호작용을 지원하는 플랫폼을 뜻합니다. 표의 수치는 발표가 소개한 Commure의 운영 규모입니다. 멀티리전 액티브는 여러 지역에서 서비스를 동시에 운영한다는 뜻이며, TiB는 메모리·저장 용량 단위입니다.

여기서 상태 저장 시스템은 Pod가 바뀌어도 데이터가 남아 있어야 하는 서비스입니다. ClickHouse와 CockroachDB 같은 데이터베이스, ElasticSearch 검색 시스템, Kafka 메시지 시스템, Prometheus 모니터링 시스템이 대상입니다. 목표는 약 500개 디스크의 데이터를 복사하는 대신, 기존 디스크를 사용하는 드라이버와 Kubernetes의 연결 정보를 전환하는 것입니다.

왜 직접 바꿀 수 없을까?

바꾸고 싶은 것은 주소가 아니라 연결 방식입니다

프로비저닝(provisioning)은 요청에 맞는 디스크와 PV를 준비하는 과정이고, provisioner는 그 일을 담당하는 드라이버입니다. StatefulSet의 volumeClaimTemplates는 Pod별 PVC를 만들기 위한 신청서 원본입니다. storageClassName은 사용할 주문 양식의 이름입니다.

PV의 claimRef는 “이 창고는 어느 신청서에 배정되었는가”를 적은 예약표입니다. 이름과 네임스페이스뿐 아니라 UID까지 기록하면, 같은 이름의 신청서를 다시 내더라도 이전 신청서와 구별합니다. 원문의 spec.persistentVolumeSource.azureDisk.diskURI는 볼륨 소스 구조를 설명한 표현이며, 실제 PV YAML에서는 spec.azureDisk.diskURI처럼 적습니다.

immutable(불변)은 생성 후 해당 항목을 수정할 수 없다는 뜻입니다. 발급된 등록증에서 시설 종류를 덧칠해 바꿀 수 없는 것과 비슷합니다. StorageClass의 provisioner나 PV의 볼륨 소스를 직접 고치지 못하므로, 새 객체를 준비해 연결을 넘겨야 합니다. Kubernetes 스토리지 리소스는 스코프가 나뉜다. PVC는 네임스페이스 스코프, PV와 StorageClass는 클러스터 스코프다.

동적 볼륨 프로비저닝의 흐름:

  1. StatefulSet의 volumeClaimTemplates가 storageClassName: legacy-storage-class를 참조한다.
  2. 해당 StorageClass의 provisioner가 kubernetes.io/azure-disk(in-tree)다.
  3. 프로비저닝된 PV는 spec.persistentVolumeSource.azureDisk.diskURI로 실제 Azure 디스크를 가리킨다.
  4. PV의 claimRef가 PVC의 name, namespace, uid까지 포함해 강하게 바인딩된다.

핵심 제약은 대부분의 필드가 immutable이라는 점이다. StorageClass의 provisioner를 바꿀 수 없고, 기존 PV의 볼륨 소스를 in-tree에서 CSI로 바꿀 수도 없다.

Kubernetes의 영속성 원칙: 스토리지는 durable하고 안정적인 리소스이며, Pod는 일시적이고 교체 가능한 존재다.

재바인딩을 가능하게 하는 내부 동작

3.1 StorageClass 객체는 수동적(passive)이다

StorageClass는 프로비저닝 시점에만 참조된다. 이미 바인딩된 PV/PVC는 StorageClass를 다시 읽지 않는다. 따라서 같은 이름으로 지우고 다시 만들 수 있다.

yaml
# Legacy
kind: StorageClass
metadata:
  name: legacy-storage-class
provisioner: kubernetes.io/azure-disk
parameters:
  storageaccounttype: Premium_LRS
  kind: Managed
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
yaml
# New
kind: StorageClass
metadata:
  name: legacy-storage-class
provisioner: disk.csi.azure.com
parameters:
  skuName: Premium_LRS
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

3.2 PV의 claimRef가 바인딩 동작을 결정한다

claimRef에 uid와 resourceVersion이 있으면 특정 PVC 인스턴스에 확정 바인딩된다(Firm binding). 반대로 name과 namespace만 남기고 uid와 resourceVersion을 생략하면 그 PV는 "해당 이름의 PVC가 나타나면 바인딩되겠다"는 예약 상태(PV available)가 된다.

yaml
# Firm binding
kind: PersistentVolume
spec:
  claimRef:
    kind: PersistentVolumeClaim
    name: data-pvc
    namespace: production
    uid: 8cbb0f8e...
    resourceVersion: "123456"
  azureDisk:
    diskURI: /subscriptions/.../disks/data-disk
yaml
# PV available (예약된 상태)
kind: PersistentVolume
spec:
  claimRef:
    kind: PersistentVolumeClaim
    name: data-pvc
    namespace: production
    # uid: OMITTED
    # resourceVersion: OMITTED
  csi:
    driver: disk.csi.azure.com
    volumeHandle: /subscriptions/.../disks/data-disk

이것이 이 발표가 말하는 "honeypot PV"다. 같은 물리 디스크를 CSI 드라이버로 가리키면서, 미래에 생성될 동일 이름의 PVC를 기다린다.

3.3 pvc-protection finalizer

PVC를 삭제해도 이를 사용하는 Pod가 살아 있으면 kubernetes.io/pvc-protection finalizer 때문에 deletionTimestamp만 찍히고 status.phase: Bound 상태로 남는다. 즉 PVC 삭제와 Pod 삭제가 함께 일어나야 실제로 정리된다.

yaml
kind: PersistentVolumeClaim
metadata:
  name: data-db-0
  namespace: production
  deletionTimestamp: "2026-09-05T18:42:00Z"
  finalizers:
    - kubernetes.io/pvc-protection
status:
  phase: Bound

세 동작을 비유로 연결하기

StorageClass는 최초 주문 때 읽는 양식입니다. 양식을 같은 이름의 새 버전으로 교체해도 이미 연결된 디스크가 자동으로 새 디스크로 바뀌지는 않습니다. 다만 교체 이후 새로 프로비저닝하는 요청은 새 설정을 사용합니다. WaitForFirstConsumer는 디스크를 사용할 Pod의 배치 조건을 고려할 때까지 바인딩·프로비저닝을 기다리는 방식입니다.

claimRef에서 UID를 빼는 것은 특정 신청서 번호 대신 이름과 구역만 적은 예약석을 마련하는 것과 같습니다. 이때 resourceVersion도 생략합니다. UID가 특정 PVC 인스턴스를 구별하는 핵심이며, 이름만 맞으면 모든 조건을 무시하고 연결된다는 뜻은 아닙니다. 용량·접근 모드·StorageClass 등도 맞아야 합니다.

honeypot PV는 발표에서 붙인 별칭입니다. 보안용 유인 서버가 아니라, 앞으로 다시 생성될 PVC를 기다리는 CSI PV입니다. 같은 창고에 대해 새 출입 방식으로 등록증을 준비해 두는 셈입니다. volumeHandle에는 새 디스크 주소가 아니라 원본 Azure managed disk의 식별자가 들어갑니다.

finalizer는 퇴실 전에 반납을 확인하는 체크표와 같습니다. kubernetes.io/pvc-protection은 사용 중인 PVC가 즉시 사라지지 않도록 붙잡습니다. deletionTimestamp는 삭제 요청 시각이지 삭제 완료 시각이 아닙니다. 삭제를 요청한 PVC가 아직 Bound로 표시될 수 있으며, 이 절차에서는 해당 PVC를 쓰는 Pod도 종료되어야 정리가 진행됩니다. finalizer를 강제로 지우는 방식으로 설명한 절차가 아닙니다.

05 / GUIDE

알고리즘: 다섯 단계로 연결 바꾸기

실행 예제를 읽기 전에

아래 절차는 발표의 동작 원리를 풀어 쓴 것입니다. YAML은 핵심 필드 중심의 발췌입니다. 실제 적용할 StorageClass에는 apiVersion: storage.k8s.io/v1이 필요하고, PV에는 apiVersion: v1, 고유한 metadata.name, 용량·접근 모드·StorageClass와 디스크 속성 등 환경에 맞는 완전한 명세가 필요합니다. /subscriptions/...는 실제 Azure 디스크 식별자로 바꿔야 합니다.

reclaim policy(회수 정책)는 신청서가 없어졌을 때 창고를 어떻게 처리할지 정하는 규칙입니다. Delete는 창고와 내용까지 철거하는 쪽이고, Retain은 사용 관계가 끝나도 창고를 남기는 쪽입니다. 따라서 이전 PV를 Retain으로 바꾸는 것은 데이터를 지키는 핵심 단계입니다. StorageClass의 reclaimPolicy를 바꾸는 것과 이미 존재하는 PV의 정책을 바꾸는 것은 별개입니다.

PV_NAME, PVC_NAME, POD_NAME은 전환 대상의 이름을 담는 셸 변수입니다. PVC와 Pod 명령은 대상 네임스페이스에서 실행해야 합니다. 다음 예제는 본문의 예시와 같이 production을 사용합니다.

Step 1. 레거시 StorageClass 삭제

bash
kubectl delete sc legacy-storage-class

Step 2. 같은 이름으로 CSI StorageClass 생성

bash
kubectl apply -f - <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: legacy-storage-class
provisioner: disk.csi.azure.com
parameters:
  skuName: Premium_LRS
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
EOF

Step 3. 레거시 PV의 reclaim policy를 Retain으로 변경

PVC를 지웠을 때 실제 Azure 디스크가 삭제되지 않도록 보호한다. 이 단계를 빠뜨리면 데이터가 사라진다.

bash
kubectl patch pv $PV_NAME -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

Step 4. 새 CSI PV("honeypot") 생성

원본 managed disk를 그대로 가리키고, claimRef에서 uid와 resourceVersion을 생략한다.

yaml
kind: PersistentVolume
spec:
  claimRef:
    kind: PersistentVolumeClaim
    name: data-app-0
    namespace: production
    # uid: OMITTED
    # resourceVersion: OMITTED
  csi:
    driver: disk.csi.azure.com
    volumeHandle: /subscriptions/.../disks/data-disk

Step 5. 재바인딩 트리거

레거시 PVC와 StatefulSet Pod를 함께 삭제한다. pvc-protection finalizer 때문에 둘 다 지워야 진행된다.

bash
kubectl delete pvc "$PVC_NAME" -n production --wait=false
kubectl delete pod "$POD_NAME" -n production

명령 보완: 원문은 kubectl delete pvc $PVC_NAME 다음에 Pod 삭제를 제시합니다. 기본 삭제 명령은 삭제 완료를 기다릴 수 있으므로, 첫 명령에 --wait=false를 넣어 다음 Pod 삭제 명령으로 진행하게 했습니다. 이는 finalizer를 없애는 옵션이 아니라 클라이언트가 기다리지 않게 하는 옵션입니다.

이후 StatefulSet 컨트롤러가 새 Pod와 새 PVC를 만들고, 새 PVC는 대기 중이던 honeypot PV를 찾아 바인딩된다. 디스크는 그대로이므로 데이터가 보존되고, 중단은 Pod 재시작 시간뿐이다.

그림으로 본 흐름

  1. 레거시 PV의 reclaim policy를 retain으로 설정한다.
  2. 원본 managed disk를 가리키는 CSI honeypot PV를 만든다. claimRef의 uid와 resourceVersion은 생략한다.
  3. 레거시 PVC와 StatefulSet Pod를 삭제해 재바인딩을 트리거한다.
  4. StatefulSet 컨트롤러가 새 Pod와 PVC를 만들고, PVC가 honeypot PV를 찾아 바인딩된다.
06 / GUIDE

결과와 중단 범위

전체 마이그레이션에 2개월이 걸렸다. 진행률 곡선은 S자 형태였다. 초기 4~5주는 0%에 머물며 검증과 자동화 준비에 쓰였고, 이후 급격히 상승해 약 38%에 도달했다. 중반에는 40%대에서 완만하게 진행되다가, 마지막 구간에서 다시 가파르게 올라 100%를 달성했다.

진행률을 어떻게 읽어야 할까요?

2개월은 전체 디스크를 순차적으로 전환한 프로젝트 기간입니다. 개별 서비스가 2개월 동안 멈췄다는 뜻이 아닙니다. 초기 4~5주의 준비, 약 38%까지의 상승, 40%대의 완만한 구간, 마지막 100% 달성은 발표의 진행률 설명을 그대로 따른 것입니다.

발표 제목은 “Zero-Downtime”이지만 절차에는 Pod 재시작이 포함됩니다. 개별 Pod에는 재시작·재연결에 따른 중단이 있습니다. 서비스 전체의 무중단 여부는 복제본, 장애 대응, 트래픽 처리 방식에 달려 있습니다. 이 방법의 직접적인 이점은 디스크 데이터를 복사하지 않고 보존하며 연결 객체를 교체한다는 점입니다.

다른 전략과 비교

표는 이번 발표의 운영 조건에 따른 평가입니다. High는 높음, Low는 낮음, Medium은 중간, Minimal은 최소 수준, Extreme은 극도로 높음이라는 뜻입니다. 보편적인 보장이나 모든 환경의 우열로 읽기보다는 핵심 서비스에 적용할 때의 비교로 보세요.

Microsoft Static Volume은 정적으로 볼륨을 준비하는 접근, Orphan and Adopt는 기존 자원의 관리 관계를 끊고 다시 인계하는 접근, Backup and Restore는 데이터를 백업한 뒤 복원하는 접근입니다. Forking the Control Plane은 Kubernetes의 핵심 제어 소프트웨어를 직접 수정해 운영하는 방식입니다. In-Place PVC Re-Binding은 디스크를 유지한 채 PVC와 PV의 연결을 다시 만드는 방식입니다.

전략 다운타임 영향 데이터 리스크 운영 복잡도 핵심 서비스 적합성
Microsoft Static Volume High (전체 재배포) Low Medium Low
Orphan and Adopt High (장기 중단 위험) Low High Very Low
Backup and Restore High (백업+복원 시간) Medium (일관성 문제) Medium Low
Forking the Control Plane Low (완벽할 경우) Very High (코어 K8s 수정) Extreme (K8s 포크 필요) Very Low
In-Place PVC Re-Binding Minimal (Pod 재시작) Low (디스크에 데이터 보존) High (깊은 전문성 필요) High

실패 사례와 타이밍

  • PV Multi-Attach 실패: 이전 attach가 정리되기 전에 새 Pod가 볼륨을 붙이려 할 때 발생한다.
  • Pod 재생성과 PVC 사이의 레이스 컨디션: StatefulSet 컨트롤러가 PVC보다 먼저 또는 늦게 움직이면서 생기는 타이밍 문제다.

두 실패는 모두 “언제 완료됐는가”의 문제입니다

Multi-Attach는 디스크가 이전 노드에 연결된 상태에서 새 노드에도 연결하려고 할 때 나타날 수 있습니다. 삭제 명령이 접수됐다고 이전 연결의 해제가 끝난 것은 아닙니다. Pod 종료와 볼륨 연결 해제 상태를 구분해서 관찰해야 합니다.

레이스 컨디션(race condition)은 여러 자동 처리 과정의 실행 순서에 따라 결과가 달라지는 현상입니다. 접수 창구가 이전 신청서를 정리하는 동안 담당자가 새 신청서를 만들려는 상황과 비슷합니다. StatefulSet의 Pod/PVC 재생성과 기존 PVC 삭제 완료 시점이 맞지 않으면 전환이 지연되거나 예상과 다른 흐름이 생길 수 있습니다. 자동화는 명령을 연달아 보내는 것뿐 아니라 각 단계의 실제 완료 상태를 확인해야 합니다.
