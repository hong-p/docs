CINDER / PTG

Per-volume QoS

Read the specBack to contents

Hello everyone. I would like to propose per-volume QoS support in Cinder.

We need this feature in our environment, so we made local changes and are using them now. We have implemented it in the NetApp, Dell PowerFlex, and Dell PowerStore drivers. We would like to bring this feature upstream.

Our current code stores QoS values in volume metadata to keep the changes small. For upstream, the spec proposes adding new database fields and a new API action to change QoS. It also adds an optional QoS field to the volume create API.

Let me briefly explain the main points.

Today, we need different volume types for different QoS values. To change QoS on an existing volume, we need to change its volume type.

With this proposal, we can set the maximum IOPS and throughput for each volume without changing its type. We can set these values when creating a volume, or change them while the volume is in use, without detaching it. These limits cover reads and writes together. Burst settings stay as they are.

Users can change the values within a range set by the administrator in the volume type. If no range is set for a limit, only an administrator can set it. Administrators can also set values outside the range.

Values set on a volume take priority over the matching QoS values in its volume type. If we clear a value, the volume uses the type's setting for that limit again.

For now, this proposal only covers QoS applied by the storage backend. We plan to add a common driver method to update QoS. When creating a volume with QoS values, Cinder will choose only a backend that supports this feature.

For the first upstream drivers, the current spec proposes NetApp ONTAP and Dell PowerFlex.

We would appreciate your feedback on this feature and the proposed design. Is there anything we should change or consider?

Thank you.

Checked against the 2027.1 per-volume QoS spec on October 10, 2026. This is a proposal; upstream support is planned.

MANILA / PTG

Share Cascade Delete

Read the specBack to contents

Hi everyone.

I’d like to propose a cascade delete option for Manila. With this option, users can delete a share and its snapshots in one request.

We already use this feature in our local version of Manila. We would like to add it to upstream as well. Cinder already has a similar feature, so I suggest following the same basic approach.

Our local version only supports the NetApp driver. We also kept the changes to Manila small. Because of this, our local version is a little different from this spec.

There are three main points in this proposal.

First, Manila deletes the snapshots one by one, and then deletes the share. If a snapshot cannot be deleted, the process stops and the share is kept.

Second, it uses the existing driver methods for deleting snapshots and shares. There is no need to add a new driver method.

Third, the first version has a limited scope. It does not support shares with replicas or deferred deletion. We can discuss support for those later.

One difference from Cinder is how we retry after a failure.

Cinder uses both cascade and force to retry. But force delete works differently in Manila. In Manila, force can remove database records even if deletion on the storage backend fails.

So I suggest retrying with the same cascade option, without adding a force option. By default, only admins would be allowed to retry a failed or stopped cascade delete. Regular members could still use cascade for a normal delete.

The retry would try to delete the remaining snapshots, and then the share. If deletion fails again, it would stop and keep the database records.

I’d like to hear your thoughts, especially on this retry approach and the scope of the first version.

Thank you.

Checked against the 2027.1 share cascade delete spec on October 10, 2026. This is a proposal; upstream support is planned.
