CINDER / PTG

Per-volume QoS

Read the specBack to contents

Hello everyone. I would like to propose per-volume QoS support in Cinder.

We need this feature in our environment, so we made a downstream patch and are using it now. We have implemented it in the NetApp, Dell PowerFlex, and Dell PowerStore drivers. We would like to bring this feature upstream.

Our current code stores QoS values in volume metadata to keep the changes small. For upstream, we propose new database fields and a new API to change QoS. We also want to add a QoS option when you create a volume.

Let me briefly explain the main points.

Today, we need different volume types for different QoS values. To change QoS on an existing volume, we need to change its volume type.

With this proposal, we can set the maximum IOPS and throughput for each volume without changing its type. We can set these values when creating a volume, or change them while the volume is in use, without detaching it. Each limit counts reads and writes together.

The administrator turns this on for a volume type, and sets a minimum, a maximum, and a default value. Users can choose any value between the minimum and the maximum. Administrators can choose any value.

If you set a value on a volume, it takes priority over the volume type. If you don't set one, or you clear it, the volume uses the type's default.

When you retype a volume, it follows the new type. You can give new values in the retype request. If you don't, the new type's default is used.

For now, this is only for QoS on the storage side. Each driver adds one method to update QoS. Cinder puts these volumes only on backends that support it.

We want to start with NetApp ONTAP and Dell PowerFlex.

We would appreciate your feedback on this feature and the proposed design.

Thank you.

Expected questions

Q. Why not use volume metadata or admin metadata?

왜 볼륨 메타데이터나 admin metadata를 쓰지 않나요?

A. Metadata is free-form text. There is no type check, no range check, and no API contract. With real columns, we get integers, validation, policy, and a microversioned API.

메타데이터는 자유 형식 텍스트라 타입 검사, 범위 검사, API 계약이 없습니다. 컬럼을 쓰면 정수 타입, 검증, 정책, microversion으로 관리되는 API를 얻습니다.

Q. Why put the range in volume type extra specs, not in the QoS spec?

범위를 왜 QoS spec이 아니라 볼륨 타입 extra spec에 두나요?

A. Users need to see the range. Users cannot read QoS specs, but we can show selected extra specs to them. Also, some drivers reject unknown keys in the QoS spec, for example NetApp.

사용자가 범위를 볼 수 있어야 합니다. 사용자는 QoS spec을 읽을 수 없지만, extra spec은 골라서 보여 줄 수 있습니다. 또 NetApp처럼 QoS spec에 모르는 키가 있으면 거부하는 드라이버가 있습니다.

Q. How does this work with front-end QoS?

front-end QoS와는 어떻게 함께 동작하나요?

A. We don't change front-end QoS. The hypervisor still applies it. So the real limit is the lower of the two.

front-end QoS는 바꾸지 않습니다. 하이퍼바이저가 계속 적용합니다. 그래서 실제 상한은 둘 중 낮은 값입니다.

Q. What happens if applying QoS fails after the volume is created?

볼륨을 만든 뒤 QoS 적용이 실패하면 어떻게 되나요?

A. The same as today when a driver fails to apply the type's QoS. The volume goes to error and we create a user message. We don't reschedule, because the volume already exists.

지금 드라이버가 타입 QoS 적용에 실패할 때와 같습니다. 볼륨은 error가 되고 사용자 메시지를 남깁니다. 볼륨이 이미 있으므로 재스케줄하지 않습니다.

Q. What about burst limits?

burst 상한은요?

A. Burst is out of scope for now. Burst settings in the QoS spec are not changed. We can add burst fields later in a new microversion.

burst는 지금은 범위 밖입니다. QoS spec의 burst 설정은 바뀌지 않습니다. 나중에 새 microversion으로 burst 필드를 추가할 수 있습니다.

Q. Can we extend this later, for example with read and write limits?

나중에 read/write 분리 상한 같은 걸로 확장할 수 있나요?

A. Yes. The API uses a qos object, so we can add new fields and new columns in a later microversion.

네. API가 qos 객체를 쓰므로, 이후 microversion에서 새 필드와 컬럼을 추가하면 됩니다.

Q. Do we need a total IOPS quota per project?

프로젝트 단위 총 IOPS 쿼터가 필요하지 않나요?

A. Good point, but it is out of scope for this spec. The range limits each volume, and the notifications let billing systems track changes. A project quota could be a follow-up.

좋은 지적이지만 이번 스펙의 범위 밖입니다. 범위가 볼륨마다 상한을 제한하고, 알림으로 과금 시스템이 변경을 추적할 수 있습니다. 프로젝트 쿼터는 후속 작업으로 할 수 있습니다.

Q. Why don't clones and snapshots inherit the limits?

클론과 스냅샷에서 만든 볼륨은 왜 상한을 물려받지 않나요?

A. To keep it simple. A new volume starts from its type's default, and you can give values when you create it.

단순하게 하려는 것입니다. 새 볼륨은 타입 기본값으로 시작하고, 생성할 때 값을 줄 수 있습니다.

Q. What about replication and failover?

복제(replication)와 failover는요?

A. The driver applies the limits to the secondary too. So the limits stay after failover.

드라이버가 secondary에도 상한을 적용합니다. 그래서 failover 뒤에도 상한이 유지됩니다.

Q. How will you test this in the gate? LVM doesn't support it.

게이트에서는 어떻게 테스트하나요? LVM은 지원하지 않는데요.

A. Right, LVM doesn't support it. The RBD driver already has back-end QoS, so we will try to add support for RBD too, if possible. Then it can be tested in the upstream Ceph job.

맞습니다, LVM은 지원하지 않습니다. RBD 드라이버는 이미 back-end QoS가 있으니, 가능하면 RBD도 지원해 보겠습니다. 그러면 upstream Ceph 잡에서 테스트할 수 있습니다.

Checked against the 2027.1 per-volume QoS spec on October 15, 2026. This is a proposal; upstream support is planned.

MANILA / PTG

Share Cascade Delete

Read the specBack to contents

Hi everyone.

I’d like to propose adding a cascade option to share delete in Manila. With this option, users can delete a share and its snapshots in one request.

We already use this feature in our local version of Manila. We would like to add it to upstream as well. Cinder already has a similar feature, so I suggest following the same basic approach.

Our local version only supports the NetApp driver. We also kept the changes to Manila small. Because of this, our local version is a little different from this spec.

There are three main points in this proposal.

First, Manila deletes the snapshots one by one, and then deletes the share. If a snapshot cannot be deleted, the process stops and the share is kept.

Second, it uses the existing driver methods for deleting snapshots and shares. There is no need to add a new driver method.

Third, the first version has a limited scope. It does not support shares with replicas or deferred deletion. We can discuss support for those later.

One difference from Cinder is how we retry after a failure.

In Cinder, we can retry a failed cascade delete with both cascade and force. Force lets us skip the status checks and try the delete again.

But force delete works differently in Manila. It can remove database records even if deletion on the storage backend fails.

So I suggest retrying with the same cascade option, without adding a force option. By default, only admins would be allowed to retry a failed or stopped cascade delete. Regular members could still use cascade for a normal delete.

The retry would try to delete the remaining snapshots, and then the share. If deletion fails again, it would stop and keep the database records.

I’d like to hear your thoughts, especially on this retry approach and the scope of the first version.

Thank you.

Checked against the 2027.1 share cascade delete spec on October 10, 2026. This is a proposal; upstream support is planned.

MANILA / PTG

Snapshot Create Force

Time slot: 14:30–14:55

Share cascade deletion specBack to contents

Hi everyone. While working on the share cascade deletion spec, I found an issue with the force parameter in the snapshot create API.

The API reference documents this parameter, but the controller ignores it. So if the source share is in the error state, for example, setting force=true still returns HTTP 400, saying that the share must be available. I reported this as bug 2169703.

There is also an older report, bug 1811336. In May 2019, Tom Barron commented that this had been discussed at the PTG and suggested removing the option because no clear use case had been identified. That bug expired, but the parameter is still documented today.

I’d like to discuss whether we should support this option or deprecate and remove it.

Does anyone have a real use case for creating a snapshot from a share that is not available? I can think of extending_error and shrinking_error, where the data on the backend is likely still intact, but I’d like to hear your opinions.

If we keep it, we need to define which share states should allow forced snapshot creation. This also affects the cascade deletion spec: even with force=true, snapshot creation should be blocked while the source share is being deleted.

If there is no clear use case, we could follow the earlier recommendation and remove the option through the appropriate deprecation process.

What do people think? Should we fix the API to honor force=true, with clear state restrictions, or move toward removing it?

References: Bug 2169703 · Tom Barron’s May 2, 2019 comment on bug 1811336 · Snapshot create API reference. Draft prepared on October 10, 2026.
