3분 요약

DECLARATIVE UNDERLAYS
용도별로 나누고, 원하는 상태를 선언한다.

Samsung SDS는 OpenStack(가상 서버·네트워크·저장장치를 제공하는 클라우드 플랫폼)을 떠받치는 Kubernetes(컨테이너 실행을 자동 관리하는 시스템) "언더레이(서비스를 떠받치는 기반 인프라)"를 하나의 거대한 클러스터로 운영하다 한계에 부딪혔고, Cluster API(클러스터 자체를 선언·관리하는 도구)로 용도별 클러스터를 YAML(설정을 글로 적는 형식) 선언 하나로 만들고 늘리고 업그레이드하는 구조로 재설계했다. 클러스터를 손으로 빚는 환경이 아니라 선언적이고 교체 가능한 인프라로 다룬 사례다.

문제

모든 상품이 한 클러스터에

새 기능마다 드라이버와 운영 규칙이 쌓여 업그레이드와 장애 대응이 어려워집니다.

구조

작업은 분리하고 관리는 통합

용도별 클러스터를 만들고 각 클러스터의 관리 프로그램을 Control Cluster에 모읍니다.

운영

설정 변경으로 생성·확장

원하는 버전과 서버 수를 파일에 적으면 자동화가 실제 환경을 그 모습으로 맞춰 갑니다.

용어 사전

용어를 읽기 전에: 가장 작은 단위부터

컨테이너는 프로그램과 실행에 필요한 것들을 담은 실행 단위입니다. Pod(파드)는 컨테이너를 묶은 Kubernetes의 최소 실행 단위이고, 노드는 이를 실행하는 컴퓨터입니다. 클러스터는 여러 노드를 한 시스템처럼 관리하는 묶음입니다. 워크로드는 그 위에서 실제로 실행하는 앱과 작업을 뜻합니다. 리소스는 Kubernetes가 이름과 설정, 상태를 붙여 관리하는 대상입니다.

용어표 속 표현도 풀어 읽기

컨트롤러는 원하는 상태와 실제 상태의 차이를 줄이는 프로그램입니다. API는 프로그램끼리 요청을 주고받는 창구이고, kube-apiserver는 Kubernetes의 요청 창구입니다. etcd는 클러스터 상태 저장소, controller-manager는 컨트롤러 실행 담당, scheduler는 Pod을 어느 노드에 놓을지 정하는 배치 담당입니다. 런타임은 컨테이너 실행 프로그램, 플러그인은 기능을 연결하는 추가 부품입니다. Git은 파일 변경 이력을 남기는 도구이며 커밋은 변경을 이력에 기록하는 단위입니다. CNCF는 Kubernetes 등 클라우드 네이티브 오픈소스 생태계를 지원하는 재단입니다.

문서를 읽기 전에 알아두면 좋은 용어들이다.

용어 쉬운 설명
OpenStack
서버, 네트워크, 스토리지를 가상화해서 "클라우드"로 파는 오픈소스 플랫폼. AWS 같은 서비스를 직접 만들어 쓰는 소프트웨어다.
Kubernetes (K8s)
컨테이너를 자동으로 배치하고 살려두는 오케스트레이터.
언더레이(Underlay)
위에서 돌아가는 서비스(여기서는 OpenStack)를 떠받치는 아래쪽 인프라 계층.
선언적(Declarative)
"어떻게 만들지" 절차를 적는 대신 "무엇이 되어야 하는지" 최종 상태를 적는 방식. 컨트롤러가 알아서 그 상태로 맞춘다.
Cluster API (CAPI)
CNCF 프로젝트. Kubernetes 클러스터 자체를 Kubernetes 리소스로 선언하게 해준다. Pod를 선언하면 컨테이너가 뜨듯, Cluster를 선언하면 클러스터가 뜬다.
컨트롤 플레인
클러스터의 두뇌. apiserver, etcd, controller-manager, scheduler로 구성된다.
데이터 플레인 / 워커 노드
실제 사용자 워크로드가 도는 서버들.
BM / VM
Bare Metal(물리 서버) / Virtual Machine(가상 머신).
CNI / CSI / CRI
각각 네트워크 / 스토리지 / 컨테이너 런타임을 붙이는 Kubernetes 플러그인 규격.
GitOps
원하는 상태를 Git에 커밋하면 자동화가 실제 환경을 그에 맞추는 운영 방식.
IaC
Infrastructure as Code. 인프라 형상을 코드로 남기는 것.
선언적이라는 말을 기억하는 비유

에어컨에 “24도를 유지해 줘”라고 설정하면 온도 차이를 보며 동작을 조절합니다. 비슷하게 “노드 3대를 유지해 줘”라고 선언하면 컨트롤러가 실제 개수를 확인하며 목표에 맞춥니다. 이 비유는 선언과 반복 조정의 관계를 설명하기 위한 것입니다.

배경: OpenStack과 Kubernetes

배경 용어

OpenInfra는 OpenStack 등 개방형 인프라 생태계입니다. Helm 차트는 Kubernetes에 앱을 설치할 때 쓰는 설정 묶음입니다. 텔코는 통신 사업 환경, 엣지는 사용자나 현장 기기 가까운 위치, 프로덕션은 실제 고객에게 서비스를 제공하는 운영 환경을 뜻합니다. 아래 연혁과 “사실상 표준”이라는 평가는 발표 자료의 설명입니다.

이번 행사는 KubeCon + CloudNativeCon + OpenInfra Summit + PyTorch Conference가 한 무대에 모인 자리였다. 발표는 그 정신을 그대로 따라간다.

02

문제: 커지는 클러스터

이번 절의 낯선 말

GPU는 많은 계산을 병렬로 처리하는 장치이고 드라이버는 운영체제가 장치를 사용하게 해 주는 소프트웨어입니다. NIC는 네트워크 카드, SR-IOV는 물리 장치를 여러 가상 기능으로 나누어 사용하는 기술입니다. 패킷은 네트워크로 보내는 데이터 조각이며 I/O는 데이터 읽기·쓰기입니다. DMZ는 외부에 노출되는 서비스를 내부와 구분해 두는 네트워크 구간입니다. 인증은 누구인지 확인하고, 인가(AuthZ)는 무엇을 허용할지 결정합니다. 네임스페이스는 클러스터 내부의 논리적 구획, CRD는 Kubernetes에 새 리소스 종류를 추가하는 정의입니다. Compute / Storage / Service는 각각 연산·저장·서비스 용도를 가리킵니다. 존은 인프라를 나누는 구역이며, Multi Zone은 여러 존, Private Zone은 전용 구역을 뜻합니다. 애드온은 추가 기능, 스케일링은 용량이나 개수를 늘리고 줄이는 일입니다.

2.1 비대해지는 과정

신규 상품이 하나 생길 때마다 언더레이 클러스터에 뭔가가 덧붙는다.

  • GPU 상품 → 전용 노드, GPU 드라이버, 최신 K8s 버전
  • 고성능 네트워크 상품 → SR-IOV, 전용 NIC, 패킷 성능 튜닝
  • 스토리지 상품 → 전용 CSI, 대용량 I/O
  • DMZ · 보안 상품 → 격리된 인증/인가
  • 사용자 · 존 확장 → 노드와 워크로드가 계속 증가

결과적으로 클러스터는 이렇게 커진다.

단계 구성 규모
Compute 중심
OpenStack
수십 노드
서비스 추가
+ Storage · DMZ
특수 애드온/드라이버가 붙은 수십 노드
현재
+ GPU · 고성능 네트워크 + 특수 Compute + Multi Zone + Private Zone
복잡도가 매우 높은 수백 노드

클러스터 스케일링 자체가 문제가 된다.

2.2 단일 클러스터가 아파오는 네 지점

# 문제 구체적 증상
1
컴포넌트 누적
CNI · CRI · CSI가 중복 설치, CRD 수백 개, 호스트 드라이버 계속 증가, 상품 간 의존성 확대
2
인가(AuthZ) 경계
쪼개기 어려움. Control·Compute·Service 격리가 네임스페이스 수준에서 멈춤. 실제로는 노드 수준 격리가 필요
3
버전 관리 부담
K8s 버전과 드라이버 버전이 커플링됨. 한 번 버전을 올리면 전체 재검증. 업그레이드가 계속 밀림
4
장애 경계
한 워크로드의 데이터 플레인 문제가 전체로 번짐. 장애가 전체에 영향을 줄 수 있음

발표의 핵심 문장: "Kubernetes는 확장을 위해 만들어졌지만, 진짜 비용은 운영자가 떠안아야 하는 복잡도다."

2.3 kubectl로 본 실상 (슬라이드 8)

명령과 출력 해설

kubectl은 Kubernetes에 명령을 보내는 도구입니다. get은 목록 조회, wc -l은 줄 수 세기, grep은 특정 글자가 있는 줄 찾기입니다. |는 앞 명령의 출력을 다음 명령에 전달합니다. CNPG는 PostgreSQL 데이터베이스 클러스터를 관리하는 CloudNativePG입니다. 아래의 “이름 충돌”은 두 프로젝트가 모두 cluster라는 이름을 써 짧은 조회 명령이 혼동된다는 뜻입니다. ls는 파일 목록, crictl은 컨테이너 런타임 조회 도구입니다. multus·Calico·OVN은 네트워크 계열, csi-cinder·csi-rbd는 스토리지 연결 계열, containerd·Kata Containers는 컨테이너 실행 계열 이름입니다.

$ kubectl get crds | wc -l
347

$ kubectl get crds | grep cluster
clusterclasses.cluster.x-k8s.io
clusterresourcesets.addons.cluster...
clusters.cluster.x-k8s.io      ← 이름 충돌
clusters.postgresql.cnpg.io    ← 이름 충돌

$ kubectl get cluster
# 어느 쪽? CAPI vs CNPG

$ kubectl get pods -A -owide | grep node-01
multus-58x2k          Running ← CNI
calico-node-x7k2      Running ← CNI
ovn-controller-p9q1   Running ← CNI
csi-cinder-node-4h8s  Running ← CSI
csi-rbd-node-w2m5     Running ← CSI

$ ls /opt/cni/bin
bridge calico multus ovn-k8s-cni...

$ crictl info | grep -i runtime
containerd / kata-containers ← CRI

CRD가 수백 개이고 cluster라는 이름이 두 프로젝트에서 충돌한다. 노드 하나에 CNI·CSI·CRI가 겹겹이 쌓여 있다.

03

접근: 용도별로 나누기

분리된 작업장, 한곳에 모인 관리실

비유하자면 GPU·네트워크·스토리지는 서로 다른 작업장입니다. 작업장마다 필요한 장비는 따로 두고, 관리실은 하나의 건물에 모을 수 있습니다. 여기서 Control Cluster는 다른 클러스터의 관리 구성 요소를 실행하는 Kubernetes 클러스터입니다. 마스터는 컨트롤 플레인을 담당하는 노드를 부르는 표현이고, 플릿은 여러 클러스터의 집합입니다. RBAC는 역할별 접근 권한 규칙, 인증서는 통신 상대의 신원을 확인하는 전자 증명입니다.

3.1 방향

"용도별로 클러스터를 나눈다. 클러스터를 단순하게 유지하자."

3.3 Cluster API가 이 대가를 없앤다 (슬라이드 11)

Hosted control plane이란?

hosted control plane은 한 클러스터의 관리 구성 요소를 다른 관리 클러스터 안에서 실행하는 방식입니다. 발표에서는 Cluster API와 직접 만든 provider(자원 생성·관리를 실제 환경에 연결하는 구현체)를 결합합니다. 관리 작업의 반복과 전용 마스터 서버 부담을 줄이는 구조로 읽으면 됩니다.

핵심 아이디어: 컨트롤 플레인을 물리 마스터 노드가 아니라 "Control Cluster의 Pod"로 돌린다.

  • Control Cluster도 그냥 Kubernetes다.
  • Cluster A/B/C의 마스터(etcd, apiserver, controller)가 Control Cluster 안에 Pod로 뜬다.
  • 클러스터별 물리 마스터 서버가 사라진다 → 컨트롤 플레인 통합(Consolidated ControlPlane).
  • 이 모든 것이 Cluster API로 선언적으로 생성·관리된다.

이 방식을 업계 용어로 hosted control plane이라 부른다.

3.4 재설계 4원칙 (슬라이드 12)

원칙 속 용어

커널은 하드웨어와 프로그램 사이를 관리하는 운영체제의 핵심입니다. 노드 풀은 같은 설정으로 관리하는 노드 묶음입니다. 이 절의 장애 경계는 발표가 제시한 데이터 플레인 격리 원칙입니다.

  1. 노드 수준 요구사항은 격리된다 — 드라이버·런타임·특수 커널은 필요한 노드에만 설치한다.
  2. 장애는 클러스터 경계에서 멈춘다 — 데이터 플레인 장애를 관리 플레인에서 떼어놓는다.
  3. 각 서비스가 자기 기술 스택을 소유한다 — Kubernetes, CNI, CSI 버전을 독립적으로 고른다.
  4. 업그레이드는 작고 반복 가능하다 — 클러스터 또는 노드 풀을 하나씩 교체한다.

아키텍처와 YAML

아키텍처 그림의 이름 읽기

아키텍처는 구성 요소의 배치와 연결 구조, KubeVirt는 Kubernetes에서 가상 머신을 관리하는 기술입니다. 학습은 데이터로 AI 모델을 만드는 과정이고 추론은 완성된 모델로 결과를 내는 과정입니다. 프록시는 요청을 중계하는 프로그램입니다. 4.2 Control Cluster 내부 (슬라이드 15)

관리 구성 요소를 Pod로 실행한다는 뜻

Deployment는 정해 둔 수의 Pod을 유지하는 리소스, StatefulSet은 저장 상태와 고유한 정체성이 필요한 Pod을 관리하는 리소스입니다. metrics-server는 자원 사용 지표를 모으는 구성 요소입니다. LB는 요청을 나눠 주는 로드 밸런서, VIP는 접속 창구가 되는 가상 IP, Service는 Pod에 접근할 고정 창구입니다. TCP는 통신 규약이고 6443·8132는 접속 용도를 구분하는 포트 번호입니다. ServiceAccount는 프로그램용 계정, Secret은 인증정보 등 민감한 값을 담는 리소스입니다. anti-affinity는 복제본을 분산 배치하는 규칙, requests는 필요한 자원 요청량, PDB는 계획된 중단 때 유지해야 할 Pod 수를 정하는 규칙입니다. join / watch는 노드 합류·상태 변화 구독입니다.

Namespace: control-cluster 안에 이런 것들이 뜬다.

4.3 Konnectivity: 두 개의 네트워크, 하나의 API 서버 (슬라이드 16)

네트워크 두 개를 잇는 전용 통로

Workload Cluster는 실제 작업을 실행하는 용도별 클러스터입니다. 오버레이 네트워크는 물리 네트워크 위에 소프트웨어로 만든 별도 통신망이고, CIDR는 10.244.0.0/16처럼 IP 주소 범위를 적는 표기입니다. 서로 다른 아파트의 내부 호수만 알아서는 찾아갈 수 없듯, 한 클러스터의 내부 주소로 다른 클러스터에서 곧바로 접속할 수 없는 상황입니다. Konnectivity는 이 통신을 중계하는 터널 구성 요소입니다. UDS는 같은 시스템 안의 프로세스 간 통신 소켓, egress selector는 API 서버의 나가는 통신 경로 설정입니다. mTLS는 양쪽 신원을 확인하는 암호화 통신, gRPC는 프로그램 간 원격 호출 방식입니다. 집계 API는 외부 기능을 API 서버의 창구로 제공하는 방식, 웹훅은 이벤트에 따라 다른 서비스에 보내는 호출, exec/logs는 컨테이너 명령 실행·로그 조회입니다. 다이얼 아웃 / 인바운드는 각각 밖으로 연결하기·밖에서 들어오는 연결입니다.

여기가 기술적으로 가장 까다로운 부분이다.

문제 상황:

kube-apiserver와 metrics-server는 서로 다른 클러스터의 Pod다. 각자 자기 클러스터의 오버레이 네트워크 위에 있다.

Control Cluster Workload Cluster (예: compute)
Pod CIDR
10.128.0.0/16
10.244.0.0/16
Service CIDR
172.20.0.0/16
10.96.0.0/16
예시 Pod
kube-apiserver 10.128.3.7, etcd 10.128.3.9
metrics-server Pod IP 10.244.1.25, Service IP 10.96.0.10

apiserver(10.128.3.7, 오버레이 A)가 metrics-server(10.96.0.x, 오버레이 B)를 호출하려 하면 경로가 없다. 각 오버레이는 자기 클러스터 안에서만 존재하기 때문에 패킷이 갈 곳이 없다.

해결책 — Konnectivity 터널:

  1. Control Cluster의 konnectivity-server Pod가 apiserver와 UDS(egress selector)로 연결된다.
  2. Workload Cluster의 konnectivity-agent Pod가 밖으로 다이얼 아웃해서 :8132로 접속한다.
  3. 그 위에 mTLS gRPC 터널이 유지된다.
  4. API 서버 → 클러스터 방향 트래픽(집계 API, 웹훅, exec/logs)이 전부 이 터널을 탄다.

에이전트가 바깥으로 먼저 연결을 여는 방식이라, 워커 쪽에 인바운드 경로를 열 필요가 없다.

슬라이드 15와 16을 구분해서 읽기

15번은 Control Cluster 구성도에 metrics-server를 표시하고, 16번은 Workload Cluster 안의 metrics-server에 접근하는 네트워크 예시입니다. 위 주소 표는 16번을 따릅니다. 16번 그림 본체의 Service IP는 10.96.0.10, 하단 설명 줄은 10.96.0.20으로 서로 다릅니다. 여기서는 그림 본체와 원문 요약의 10.96.0.10을 사용했습니다.

4.4 Cluster API란 무엇인가 (슬라이드 17)

화살표는 “누구에게 맡기는가”를 뜻합니다

infrastructureRef와 controlPlaneRef는 인프라와 컨트롤 플레인 담당 리소스를 가리키는 참조입니다. InfraCluster / ControlPlane은 그 담당 대상을 표현한 이름입니다. HA는 일부 구성 요소가 멈춰도 서비스가 이어지도록 하는 고가용성입니다. MachineDeployment → MachineSet → Machine은 노드 묶음의 목표 → 같은 설정의 노드 집합 → 노드 한 대의 선언으로 이어집니다. InfraMachine은 실제 서버 준비를 맡는 인프라 리소스입니다. ReplicaSet은 동일한 Pod 복제본 수를 유지합니다. reconcile은 목표와 실제 상태를 반복 비교해 맞추는 과정입니다. AWS·OpenStack·vSphere는 provider가 연결할 수 있는 서로 다른 인프라 환경의 예입니다.

CNCF 프로젝트로, 클러스터 자체를 Kubernetes 리소스로 선언한다.

Pod를 선언하면 컨테이너를 얻듯, Cluster를 선언하면 클러스터를 얻는다.

① 컨트롤 플레인 자동화

Cluster --infrastructureRef--> InfraCluster
   |
   +--controlPlaneRef--> ControlPlane

마스터 생성 · HA · 버전 관리, 인프라 준비를 담당한다.

② 노드 자동화

MachineDeployment --> MachineSet --> Machine --infrastructureRef--> InfraMachine

replicas 수만큼 실제 서버/VM을 노드로 만든다. (Deployment → ReplicaSet → Pod 구조와 똑같은 모양이다.)

동작 원리: 컨트롤러가 선언된 상태와 실제 상태를 계속 비교해서 수렴시킨다(reconcile).

Provider: AWS, OpenStack, vSphere 등 인프라 차이를 흡수하는 열린 계약이다. 직접 구현할 수도 있다. → 발표팀은 자체 베어메탈 언더레이 provider와 컨트롤 플레인 provider를 직접 만들었다.

4.5 클러스터를 YAML로 선언하기 (슬라이드 18)

YAML은 “원하는 모습”을 적는 주문서

kind는 종류, metadata.name은 이름, spec은 원하는 설정입니다. version은 버전, replicas는 원하는 개수, endpoint는 접속 주소입니다. 프로비저닝은 서버와 설정을 준비해 사용할 수 있게 만드는 과정입니다. 아래는 원문에 있는 축약 예시입니다. ...처럼 생략된 부분이 있으며, 발표팀의 자체 리소스를 포함하므로 완전한 설치 파일로 읽기보다 참조 관계와 값의 의미에 집중하세요.

kind: Cluster
metadata:
  name: sample
spec:
  controlPlaneRef:
    kind: SCPControlPlane
  infrastructureRef:
    kind: SCPCluster
---
kind: SCPControlPlane
spec:
  version: v1.35.0
  podCidr: 10.244.0.0/16
  replicas: 3
---
kind: SCPCluster
spec:
  controlPlaneEndpoint:
    host: 192.0.2.10

kind: UnderlayMachineTemplate
metadata:
  name: sample-worker
spec:
  template:
    spec:
      underlayMachine:
        ...
---
kind: MachineDeployment
spec:
  clusterName: sample
  replicas: 3
  template:
    spec:
      infrastructureRef:
        kind: UnderlayMachineTemplate
        name: sample-worker

실제로 만지는 값은 네 개뿐이다.

필드 의미
controlPlaneRef / infrastructureRef
1) 컨트롤 플레인 프로비저닝, 2) 인프라(머신 노드) 프로비저닝
version: v1.35.0
이 값을 바꾸는 것이 곧 업그레이드다
replicas: 3
컨트롤 플레인이면 apiserver 개수, MachineDeployment면 노드 개수
underlayMachine
노드 형태 (베어메탈 / KubeVirt VM)

템플릿을 재사용하고 name, endpoint, replicas만 바꾸면 된다.

모든 SCP* / Underlay* kind는 발표팀이 만든 자체 CRD + 컨트롤러다. 컨트롤 플레인은 Deployment로, etcd는 StatefulSet으로, 노드는 MachineDeployment로 구현된다.

6.2 클러스터 생성 흐름 (슬라이드 22)

자동화 사이의 역할 분담

MGMT 클러스터는 관리 클러스터를 뜻합니다. Ready는 준비 완료, 핸드오버는 다음 담당자에게 제어를 넘기는 일, status는 리소스의 현재 상태입니다. 여기서는 Cluster API가 클러스터를 준비하고 GitOps가 앱 배포를 이어받습니다.

단계 주체 내용
1
사람
Git에 선언을 커밋한다 — 운영자의 일은 여기서 끝난다
2
자동
컨트롤 플레인이 MGMT 클러스터에 생성된다
3
자동
물리 서버가 준비된다 (베어메탈 예약 · 프로비저닝)
4
자동
노드가 클러스터에 join한다
5
자동
Ready → 핸드오버. GitOps가 이어받아 앱을 배포한다

진행 상황은 Kubernetes 오브젝트 status로 계속 보인다.

6.3 유스케이스: 멀티 AZ (슬라이드 23)

AZ를 늘린다는 뜻

AZ(Availability Zone, 가용 영역)는 장애 영향을 분리하도록 나눈 인프라 구역입니다. 멀티 AZ는 이런 구역 여러 곳을 사용하는 구성입니다. Service는 서비스용, Edge / Storage는 현장 가까운 처리·저장용 클러스터를 가리킵니다.

clusters/
 ├ az-a/
 ├ az-b/
 └ az-c/
  • AZ A: Service, Compute, AI/GPU, Edge/Storage — 동일한 4개 용도 클러스터
  • AZ B: 같은 선언, 크기만 다름
  • AZ C (신규): Git에 선언을 추가하면 자동 구축

용량과 네트워킹만 준비되면, 새 AZ는 Git을 통해 같은 청사진을 그대로 재사용한다.

07

독립적인 기술 스택

네트워크 조합과 서비스 범위

기술 스택은 함께 사용하는 소프트웨어 조합입니다. Cilium / Calico는 Kubernetes 네트워크 구현, multus는 Pod에 여러 네트워크를 연결하는 구성 요소, OVS는 소프트웨어 네트워크 스위치입니다. RDMA는 다른 장치의 메모리로 데이터를 직접 전달하는 기술이며 device plugin은 특수 장치를 Kubernetes에 알려 주는 플러그인입니다. 리전은 지리적 서비스 구역, AZ(가용 영역)는 리전 안에서 장애 영향을 분리하도록 나눈 구역입니다. Zonal은 AZ 단위, Regional은 리전 단위 범위를 뜻합니다. 네트워크 정책은 어떤 통신을 허용할지 정한 규칙입니다.

08

자원 활용률 개선

반납과 재배치를 이해하기

CSP는 클라우드 서비스 제공자입니다. 풀은 배정할 수 있는 자원을 모아 둔 묶음입니다. drain은 노드에서 작업을 비우는 절차, cordon은 새 작업 배치를 막는 조치, delete · clean은 대상 삭제와 다음 사용을 위한 정리를 뜻합니다. 아래는 서버를 추가 구매하는 대신 기존 풀에서 노드를 다시 배정하는 발표의 예시입니다.

8.1 왜 CSP에게 중요한가 (슬라이드 27)

매출은 판매된 용량에서 나온다. 유휴 노드는 돈 주고 산 하드웨어가 아무것도 벌지 못하는 상태다. 활용률이 곧 마진이다.

커밋 하나로 리밸런싱이 일어난다.

단계 내용
1
git commit — B: 6 → 3, A: 3 → 6
2
Cluster API가 양쪽을 reconcile
3
클러스터 B가 drain — cordon · delete · clean
4
공유 풀로 노드 반납
5
클러스터 A가 확보 — 머신 생성 (BM / VM)

반납과 확보가 같은 reconcile 루프다. 발표는 기존 풀을 이용해 몇 분 뒤 재배치가 완료되고, 새 하드웨어는 필요 없는 예시로 설명한다.

  • 같은 고정 풀 — 서버 추가 구매 제로
  • 유휴 시간 ↓ = 마진 ↑
  • 양방향 — 숫자 하나, 커밋 하나

09

IaC와 저장소

파일 이름이 곧 자원 분류

머신 타입은 CPU·메모리 등 서버 사양의 종류입니다. standard / highmem / highcpu는 일반형·메모리 중심·CPU 중심 풀을 뜻합니다. vCPU는 가상 CPU 수, GiB는 메모리 용량 단위입니다. 템플릿은 여러 자원에 재사용하는 설정 틀입니다. 아래 저장소 구조와 YAML은 발표 자료에 제시된 예시입니다.

저장소 구조 (samsung-cloud/cluster-infra, 슬라이드 30 스크린샷):

base/
 ├ compute.yaml
 ├ hyper-network.yaml
 ├ ai-gpu.yaml
 └ dmz.yaml
clusters/
 ├ dev/
 ├ kr-west1/
 │   └ az-a/
 │       ├ compute/
 │       │   ├ cluster.yaml
 │       │   ├ md-standard.yaml
 │       │   ├ md-highmem.yaml
 │       │   └ md-highcpu.yaml
 │       ├ hyper-network.yaml
 │       ├ ai-gpu.yaml
 │       └ dmz.yaml
 ├ kr-west2/ · kr-east1/ · na-west1/ ...

머신 타입별로 MachineDeployment를 하나씩 둔다 (standard · highmem · highcpu).

compute/md-standard.yaml 예시:

kind: MachineDeployment
metadata:
  name: compute-az-a-standard
spec:
  clusterName: compute-az-a
  replicas: 24
  template:
    spec:
      machineType: std-v3     # 16 vCPU · 64 GiB
      version: v1.31          # Compute cluster · Cilium · zonal
      infrastructureRef:
        kind: BareMetalMachineTemplate
        name: std-v3-template

# 같은 클러스터의 형제 풀:
#   md-highmem.yaml → mem-v3  (8 vCPU · 128 GiB)  VM hosts, memory-bound
#   md-highcpu.yaml → cpu-v3  (32 vCPU · 64 GiB)  VM hosts, cpu-bound

커밋 메시지도 그대로 운영 기록이 된다. 예: scale compute standard pool 18 → 24, enable RDMA device plugin - multus + Cilium + SR-IOV, hardened network policy — exposed zone (v1.35).

터미널로 보는 운영

터미널을 처음 보는 독자를 위해

scpctl은 슬라이드에서 인프라 조회에 사용하는 명령입니다. -A는 모든 네임스페이스, -n은 특정 네임스페이스, -w는 변화를 계속 관찰한다는 뜻입니다. Provisioning / Provisioned는 준비 중·준비 완료, ScalingUp / Running은 확장 중·실행 중입니다. READY는 준비된 수, UPDATED는 목표 설정이 반영된 수입니다. SSH는 원격 서버에 로그인하는 방식, PR은 코드 변경을 검토·병합해 달라는 요청입니다. 아래 출력은 발표 예시를 옮긴 것이며 이 문서 작성 중 실행한 결과가 아닙니다.

11

AI 에이전트 로드맵

현재 구조 위에 얹으려는 다음 단계

AI 에이전트는 정보를 읽고 분석해 작업이나 변경을 제안하는 AI 프로그램입니다. 인벤토리는 보유 자원 목록, Prometheus는 수치 지표 수집·조회 도구, OpenSearch는 로그 등의 검색·분석 도구, APM은 앱 성능 모니터링입니다. 핫스팟은 부하가 집중되는 곳, 드리프트는 선언과 실제 상태의 어긋남입니다. git diff는 변경 전후 차이입니다. 이 절은 향후 로드맵이며 슬라이드 31의 수치는 설명용 예시입니다.

단계 내용
1. 리전 전체 클러스터
즉시 인벤토리 — 클러스터 · BM/VM · vCPU · 메모리. 선언된 상태에서 실시간 인벤토리를 얻는다
2. 실시간 상태 분석
Prometheus · OpenSearch · APM으로 클러스터/풀별 사용량 대 유휴량 분석. 핫스팟, 낭비, 드리프트를 찾는다
3. PR로 제안
제안을 git diff로: replicas 12 → 8. PR/리뷰로 사람이 루프에 남는다

인프라가 코드로 표현되어 있기 때문에 AI 에이전트가 읽고 제안할 수 있고, 제안은 PR이라는 사람이 검토 가능한 형태로 나온다.
