02 · CBT VALUE

CBT backup — why is it useful? CBT 백업은 왜 유용한가?

Conversation flow · 대화 흐름

First explain why CBT matters. Then explain two related RBD changes and ask whether they are ready for a real backup product.

먼저 CBT가 왜 중요한지 설명하고, 관련된 두 RBD 변경을 설명한 뒤 실제 백업 제품에 사용할 준비가 되었는지 묻습니다.

1. Set the context · 배경 설명하기

I want to understand the real value of Cinder CBT backup.

Cinder CBT 백업의 실제 가치를 이해하고 싶습니다.

My company is interested in using it for a backup product.

우리 회사는 이 기능을 백업 제품에 사용하려고 관심을 가지고 있습니다.

2. Explain the benefit · 장점 설명하기

One reason we are interested in CBT is backup performance.

우리가 CBT에 관심을 가지는 이유 중 하나는 백업 성능입니다.

With CBT, we only need to back up the changed blocks.

CBT를 사용하면 변경된 블록만 백업하면 됩니다.

So I think it can reduce backup time and data transfer.

그래서 백업 시간과 데이터 전송량을 줄일 수 있다고 생각합니다.

3. Explain two related Cinder changes · 서로 관련된 두 Cinder 변경 설명하기

Reference changes · 참고 변경사항

1002961 · RBD CBT 1004171 · Snapshot export/attach
My understanding · 제가 이해한 내용

These two changes are connected, so I want to explain them together.

이 두 변경은 서로 연결되어 있어서 함께 설명하고 싶습니다.

I would like to talk about two Cinder changes for RBD backup.

RBD 백업을 위한 두 가지 Cinder 변경에 대해 이야기하고 싶습니다.

The first change adds Changed Block Tracking to the RBD driver.

첫 번째 변경은 RBD 드라이버에 Changed Block Tracking을 추가합니다.

It can find only the blocks that changed between two snapshots.

두 스냅샷 사이에서 변경된 블록만 찾을 수 있습니다.

This means that an incremental backup does not need to scan the whole volume every time.

즉, 증분 백업은 매번 전체 볼륨을 검사할 필요가 없습니다.

It can send only the changed blocks, so backup time and data transfer can be reduced.

변경된 블록만 보낼 수 있으므로 백업 시간과 데이터 전송량을 줄일 수 있습니다.

The second change adds snapshot export and attach support for backups.

두 번째 변경은 백업을 위한 스냅샷 export 및 attach 지원을 추가합니다.

An RBD snapshot cannot be attached directly.

RBD 스냅샷은 직접 attach할 수 없습니다.

So it creates a temporary copy-on-write clone from the snapshot.

그래서 스냅샷으로부터 임시 copy-on-write clone을 만듭니다.

The backup flow can attach this temporary clone and use it as a source.

백업 흐름은 이 임시 clone을 attach해서 소스로 사용할 수 있습니다.

The CBT change depends on the snapshot export and attach change.

CBT 변경은 스냅샷 export 및 attach 변경에 의존합니다.

I think these two changes can make an efficient RBD backup flow.

저는 이 두 변경이 효율적인 RBD 백업 흐름을 만들 수 있다고 생각합니다.

CBT finds the changed blocks, and the temporary clone gives the backup a usable source.

CBT는 변경된 블록을 찾고, 임시 clone은 백업에 사용할 수 있는 소스를 제공합니다.

4. Ask about readiness · 준비 상태 묻기

Do you think this is the main benefit?

이것이 가장 큰 장점이라고 생각하시나요?

Do you think CBT is ready to be used by a real backup product?

CBT가 실제 백업 제품에서 사용될 준비가 되었다고 생각하시나요?

What do you think is still missing?

아직 부족한 점은 무엇이라고 생각하시나요?

5. Ask how to use it · 실제 사용 방법 묻기

How would you use CBT in a backup product?

백업 제품에서 CBT를 어떻게 사용하시겠어요?

Would the backup software call the Cinder API directly?

백업 소프트웨어가 Cinder API를 직접 호출하게 될까요?

Do we need any more APIs for real backup products?

실제 백업 제품을 위해 더 필요한 API가 있을까요?

04 · EVERPURE / PURE STORAGE

Everpure Storage and Cinder Everpure Storage와 Cinder

Conversation flow · 대화 흐름

Say our company’s position first. Then ask about the missing feature in the support matrix.

먼저 우리 회사의 입장을 말하고, support matrix에서 빠진 기능에 대해 묻습니다.

1. Explain our company’s position · 우리 회사의 입장 설명하기

We provide a CSP service by wrapping OpenStack.

우리는 OpenStack을 래핑해서 CSP 서비스를 제공하고 있습니다.

So, we are making a lot of effort to add the features our customers want to Cinder and Manila.

그래서 고객이 원하는 기능들을 Cinder와 Manila에 녹여 넣으려고 많은 노력을 하고 있습니다.

We try to avoid local changes as much as possible, and we aim to contribute upstream.

가급적이면 로컬 체인지를 지양하고 upstream에 contribution을 지향하고 있습니다.

So, we are trying to get vendors to add the features we want, or to add them ourselves.

그래서 우리가 원하는 기능들을 vendor가 넣어 주거나 우리가 넣을 수 있도록 노력하고 있습니다.

In that sense, I am very happy because Everpure seems to contribute very actively.

그런 의미에서 Everpure는 정말 열심히 contribution하는 것 같아서 너무 좋습니다.

From a developer’s point of view, I hope we can use only Everpure Storage.

개발자의 입장에서 Everpure Storage만 사용했으면 하는 바람입니다.

But I looked at the Cinder support matrix, and I found that one feature is missing from the Everpure drivers: Volume Migration (Storage Assisted).

그런데 Cinder support matrix를 봤는데 Everpure driver 중 1가지 기능이 빠져 있던데 (Volume Migration (Storage Assisted)).

When do you plan to support this feature?

이건 지원 계획이 언제 있는지?

2. Ask about Everpure’s current support · Everpure의 현재 지원 묻기

I also want to understand what Cinder features Everpure Storage supports.

Everpure Storage가 어떤 Cinder 기능을 지원하는지도 알고 싶습니다.

What Cinder features does Everpure support today?

Everpure는 현재 어떤 Cinder 기능을 지원하나요?

Which features are most important for your customers?

고객에게 가장 중요한 기능은 무엇인가요?

Are there any Cinder features that are difficult to support on Everpure?

Everpure에서 지원하기 어려운 Cinder 기능이 있나요?

Are there any new Cinder features that you want to add?

추가하고 싶은 새로운 Cinder 기능이 있나요?

Besides CBT, what Cinder feature are you working on now?

CBT 외에 지금 작업 중인 Cinder 기능은 무엇인가요?

3. Ask for the next details · 다음 내용 묻기

Is Everpure planning to support this feature?

Everpure는 이 기능을 지원할 계획이 있나요?

When do you expect to support it?

언제 지원할 예정인가요?

Is there a target release or timeline?

목표 릴리스나 일정이 있나요?

Could we help with the upstream contribution if needed?

필요하다면 upstream 기여를 우리가 도울 수 있을까요?

Are there any technical issues that we should understand?

우리가 알아야 할 기술적인 문제가 있나요?

05 · BACKUP SCHEDULING

Backup scheduling 백업 스케줄링

Conversation flow · 대화 흐름

Introduce the scheduling idea, give a simple example, and then ask why it was kept outside Cinder.

스케줄링 아이디어를 소개하고, 간단한 예를 든 다음, 왜 Cinder 외부에 두었는지 묻습니다.

1. Introduce the idea · 아이디어 소개하기

I think Cinder backup scheduling could be useful.

Cinder 백업 스케줄링이 유용할 수 있다고 생각합니다.

Cinder already has backup APIs, but users need another system to run backups on a schedule.

Cinder에는 이미 백업 API가 있지만, 사용자가 일정에 따라 백업을 실행하려면 다른 시스템이 필요합니다.

2. Give an example · 예를 들기

I was thinking about backup scheduling in Cinder.

Cinder의 백업 스케줄링에 대해 생각해 보았습니다.

It would be useful if users could create a backup schedule directly.

사용자가 직접 백업 일정을 만들 수 있다면 유용할 것 같습니다.

For example, they could say, “Back up this volume every day at 2 AM.”

예를 들어, “이 볼륨을 매일 오전 2시에 백업해 주세요”라고 설정할 수 있습니다.

What do you think about adding this kind of feature?

이런 기능을 추가하는 것에 대해 어떻게 생각하시나요?

3. Connect it to the old spec · 오래된 스펙과 연결하기

I found an old Mitaka spec for the scalable backup service.

Scalable Backup Service에 대한 오래된 Mitaka 스펙을 찾았습니다.

It mentioned scheduled backup workloads, but scheduling itself was outside the scope.

그 문서는 예약된 백업 작업을 언급했지만, 스케줄링 자체는 범위 밖이었습니다.

Do you know if there was any follow-up work after that?

그 이후에 후속 작업이 있었는지 알고 계신가요?

4. Ask about the next step · 다음 단계 묻기

Was there a reason Cinder did not add backup scheduling?

Cinder가 백업 스케줄링을 추가하지 않은 이유가 있었나요?

Was it because scheduling should be handled outside Cinder?

스케줄링은 Cinder 외부에서 처리해야 하기 때문이었나요?

Do you think that idea is still true today?

지금도 그 생각이 유효하다고 보시나요?

Would you support a new proposal for backup scheduling?

백업 스케줄링에 대한 새 제안을 지지해 주실 수 있나요?

06 · PER-VOLUME QOS

Per-volume QoS 볼륨별 QoS

Conversation flow · 대화 흐름

Describe the current type-based model, explain your per-volume idea, and compare it with AWS and Manila.

현재 유형 기반 모델을 설명하고, 볼륨별 아이디어를 말한 뒤 AWS와 Manila를 비교합니다.

1. Describe the current model · 현재 모델 설명하기

Today, Cinder QoS is mainly connected to volume types.

현재 Cinder QoS는 주로 볼륨 유형에 연결되어 있습니다.

I was thinking about allowing users to set QoS for each volume.

사용자가 각 볼륨에 QoS를 설정할 수 있도록 하는 것을 생각해 보았습니다.

2. Explain the proposal · 제안 설명하기

I have another idea about QoS.

QoS에 대한 다른 아이디어도 있습니다.

Today, QoS is mainly based on the volume type.

현재 QoS는 주로 볼륨 유형을 기준으로 합니다.

What do you think about setting QoS for each volume?

각 볼륨에 QoS를 설정하는 것에 대해 어떻게 생각하시나요?

For example, a user could set IOPS or bandwidth when creating a volume.

예를 들어, 사용자가 볼륨을 만들 때 IOPS나 대역폭을 설정할 수 있습니다.

It could also be useful to change the QoS value later.

나중에 QoS 값을 변경할 수 있어도 유용할 것 같습니다.

3. Compare with AWS · AWS와 비교하기

AWS allows users to choose some performance values for each volume.

AWS에서는 사용자가 각 볼륨의 일부 성능 값을 선택할 수 있습니다.

Why did OpenStack choose a volume-type-based model instead?

OpenStack은 왜 대신 볼륨 유형 기반 모델을 선택했나요?

Was there a technical reason?

기술적인 이유가 있었나요?

Or was it mainly an API design decision?

아니면 주로 API 설계상의 결정이었나요?

4. Ask about dynamic QoS · 동적 QoS 묻기

What do you think about changing QoS values while the volume is being used?

볼륨을 사용하는 동안 QoS 값을 변경하는 것에 대해 어떻게 생각하시나요?

Do storage backends usually support that?

스토리지 백엔드는 보통 이를 지원하나요?

Would this be difficult to add to Cinder?

이것을 Cinder에 추가하기 어려울까요?

5. Compare with Manila · Manila와 비교하기

Manila also mainly uses share types for this kind of setting.

Manila도 이런 설정에는 주로 공유 유형을 사용합니다.

Do you think Cinder and Manila should keep the type-based model?

Cinder와 Manila가 유형 기반 모델을 계속 유지해야 한다고 생각하시나요?

Or do you think per-volume settings would be useful?

아니면 볼륨별 설정이 유용하다고 생각하시나요?

07 · ENCRYPTION / KMS

KMS — one key per volume KMS — 볼륨별 키

Conversation flow · 대화 흐름

Start with Manila’s model, explain a similar Cinder model, and connect it to customer BYOK needs.

Manila 모델에서 시작해 Cinder의 비슷한 모델을 설명하고, 고객의 BYOK 요구로 연결합니다.

1. Introduce the need · 필요성 소개하기

I am also interested in encryption key support.

암호화 키 지원에도 관심이 있습니다.

Manila already has a model where a user can provide an encryption key reference.

Manila에는 사용자가 암호화 키 참조를 제공할 수 있는 모델이 이미 있습니다.

I was thinking about using a similar model in Cinder.

Cinder에도 비슷한 모델을 사용하는 것을 생각해 보았습니다.

2. Explain the model · 모델 설명하기

I have been looking at Manila’s encryption key support.

Manila의 암호화 키 지원을 살펴보고 있습니다.

Manila can accept a user-provided encryption key reference.

Manila는 사용자가 제공한 암호화 키 참조를 받을 수 있습니다.

I think Cinder could use a similar model.

Cinder도 비슷한 모델을 사용할 수 있다고 생각합니다.

The API does not need to depend on one KMS.

API가 하나의 KMS에 의존할 필요는 없습니다.

It could use Barbican or another backend through Castellan.

Castellan을 통해 Barbican이나 다른 백엔드를 사용할 수 있습니다.

3. Ask about Cinder · Cinder에 대해 묻기

What do you think about adding this model to Cinder?

이 모델을 Cinder에 추가하는 것에 대해 어떻게 생각하시나요?

Do you see any problem with it?

이 방식에 문제가 있다고 보시나요?

Would a user-provided key reference be useful for Cinder users?

사용자가 제공하는 키 참조가 Cinder 사용자에게 유용할까요?

Should Cinder support a different encryption key for each volume?

Cinder가 각 볼륨마다 다른 암호화 키를 지원해야 할까요?

Do you think the API should stay independent from a specific KMS?

API가 특정 KMS로부터 독립된 상태를 유지해야 한다고 생각하시나요?

4. Connect it to BYOK · BYOK로 연결하기

Some enterprise customers want to use their own encryption keys.

일부 엔터프라이즈 고객은 자신의 암호화 키를 사용하고 싶어 합니다.

So I think BYOK could be useful for Cinder.

몇 년이 지나면 보통 코드를 작성하는 시간이 줄어듭니다.

그래서 아직도 개발을 매우 활발히 하시는 것을 보고 흥미로웠습니다.

12 · WHEN I DON’T UNDERSTAND

When I don’t understand Simon Simon의 말을 이해하지 못했을 때

Conversation flow · 대화 흐름

먼저 다시 말하거나 천천히 말해 달라고 하고, 그다음 기술적인 의미를 내 말로 확인합니다.

1. Ask for repetition · 다시 말해 달라고 하기

죄송하지만 다시 말해 주시겠어요?

Cinder가 이것을 직접 처리하면 안 된다는 뜻인가요?

So, if I understand correctly, you mean…

제가 올바르게 이해했다면, …라는 뜻이군요.

Let me check if I understood you correctly.

제가 제대로 이해했는지 확인해 보겠습니다.

So you’re saying the main problem is the API design, right?

그러니까 가장 큰 문제는 API 설계라는 말씀이시죠?

그러면 백엔드는 지원할 수 있지만, 현재 Cinder는 이를 API로 제공할 수 없다는 뜻인가요?

So technically it is possible, but you are not sure if it belongs in Cinder. Right?

기술적으로는 가능하지만 Cinder의 범위에 들어가는지는 확실하지 않다는 뜻이죠?
