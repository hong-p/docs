Cinder CBT 백업 구조와 구현

RBD의 사전 버그 수정, Cinder 백업 프레임워크, 그리고 Everpure FlashArray 구현을 실제 코드 흐름에 맞춰 설명합니다. 먼저 기억할 요약을 보고, 그 다음 wrapper·extent·snapshot·restore 수준으로 내려갑니다.

한국어 기술 해설 RBD 1004171 + 1002961 Everpure 990982 제공된 Gerrit diff 기준
요약 설명 흐름 구조 Wrapper Extents Lifecycle RBD Everpure 차이점 Restore REST API 검토 포인트 자료
한 문장 요약
이 작업은 “CBT가 유용하다”는 설명이 아니라, 백업이 읽을 범위를 스토리지의 변경 정보로 정하고 그 범위만 기존 chunk 저장 경로로 보내도록 연결한 구현입니다.

RBD에서는 먼저 snapshot export/attach가 빠져 있던 독립 버그를 고친 뒤 CBT를 올렸고, Everpure는 snapshot export와 CBT를 한 변경에 함께 넣었습니다. 두 driver 모두 같은 Cinder 계약을 지키지만, 실제 snapshot 생성·diff 조회·접속 방식은 다릅니다.

01 · RBD PREREQUISITE

먼저 백업이 읽을 수 있게 만들었다

backup_use_temp_snapshot=True일 때 RBD에는 snapshot을 export/attach하는 구현이 없었습니다. BaseVD의 기본 반환값이 None이라 실제 증상은 뒤 단계의 TypeError로 나타날 수 있었습니다. 이 문제는 CBT와 무관하게 snapshot 백업에서도 생기므로 별도 CR로 분리했습니다.

02 · CBT CHANGE

그 다음 변경 범위를 backend에서 받았다

create_cbt_snapshot으로 기준점을 만들고, get_cbt_extents가 두 snapshot 사이의 offset / length를 반환합니다. 백업은 각 extent에서 seek → read → _backup_chunk만 실행합니다.

03 · SAME CONTRACT, DIFFERENT API

Everpure와 RBD의 공통점과 차이

공통으로 Cinder의 세 driver 메서드와 COW 기반 snapshot lifecycle을 사용합니다. RBD는 librbd diff_iterate, Everpure는 FlashArray volumes/diff를 사용하고, snapshot 이름·block granularity·window 처리도 다릅니다.

구현을 한 문장으로 요약하면

RBD snapshot export/attach의 독립 버그를 먼저 수정하고, 그 다음 storage diff API를 이용해 CBT를 추가했습니다. Backup manager는 반환된 byte 범위만 읽어 기존 chunked backup 경로로 전달합니다.

01

구현을 읽는 순서

이 문서는 다음 순서로 읽으면 전체 맥락이 이어집니다. 먼저 독립 버그를 고쳐 백업 데이터 경로를 열고, 그 위에 backend diff를 연결한 뒤, 기존 chunk 저장과 restore가 그 결과를 어떻게 소비하는지 확인합니다.

  1. 01 · PREREQUISITERBD snapshot export/attach bugfixCBT와 무관한 독립 문제를 먼저 해결
  2. 02 · CONTRACTCinder CBT driver 계약세 메서드와 RPC 연결
  3. 03 · CONSUMPTIONbackup manager + wrapperextent로 읽기 범위를 계획
  4. 04 · BACKENDRBD / Everpure 구현native diff API를 계약에 매핑
  5. 05 · RESTOREoffset write + zero 처리기존 restore path로 chain 재구성

이 페이지는 제공된 patch와 스펙을 코드 흐름으로 읽기 위한 별도 기술 문서입니다.

02

전체 구조: driver diff가 백업 chunk가 되기까지

CBT의 핵심은 backend가 반환한 extent를 새로운 저장 포맷으로 바꾸는 것이 아닙니다. 기존 chunked backup의 파일 읽기·object 저장 경로에 “어디를 읽을지”만 주입합니다.

  1. STEP 1Cinder volume driversnapshot 생성과 backend diff
  2. STEP 2Volume manager / RPCsupports + 3 CBT calls
  3. STEP 3Backup managerreference와 extent 계획
  4. STEP 4CBTVolumeFileWrapperopen file + extent list
  5. STEP 5Chunked driverseek, read, _backup_chunk

실제 데이터는 마지막 단계에서 storage backend object로 저장됩니다. wrapper 자체가 volume bytes를 저장하지는 않습니다.

위치확인된 구현역할
BaseVDcreate_cbt_snapshot, get_cbt_extents, delete_cbt_snapshot모든 volume driver가 따르는 기본 계약. 기본 구현은 지원하지 않음을 뜻합니다.
VolumeManagersupports_cbt + 세 메서드 RPC handler세 메서드가 모두 BaseVD와 다른지 class identity로 확인하고 driver에 위임합니다.
rpcapicinder-volume RPC API 3.21capability, extent 조회, snapshot 생성·삭제를 volume host로 보냅니다.
BackupManager_get_cbt_backup_info, cleanup, wrapper 생성full/incremental/re-bootstrap을 계획하고 reference provenance를 관리합니다.
ChunkedBackupDriver_backup_cbt와 metadata 저장extent마다 file을 seek하고 chunk 단위로 읽어 기존 object writer를 사용합니다.
왜 “4개의 RPC 호출”이라고 말하는가?

기능 이름은 세 개(create, get, delete)지만, capability를 확인하는 supports_cbt까지 volume manager/RPC에 추가됩니다. 따라서 Cinder volume RPC 표면에서는 네 메서드가 함께 움직입니다.

supports_cbt의 핵심 로직을 단순화한 모습
for name in ('create_cbt_snapshot', 'get_cbt_extents',
             'delete_cbt_snapshot'):
    implementation = getattr(type(self.driver), name, None)
    base_stub = getattr(driver.BaseVD, name, None)
    if implementation is None or implementation is base_stub:
        return False
return True

실제 코드는 일부만 override한 driver를 CBT capable로 잘못 광고하지 않도록 세 메서드를 모두 검사합니다.

03

Wrapper는 무엇을 들고 있는가?

CBTVolumeFileWrapper는 volume 전체를 메모리에 올리는 buffer가 아닙니다. 이미 attach되어 열린 block-device file reference를 감싸고, backend가 계산한 extent와 다음 reference 정보를 함께 전달하는 작은 adapter입니다.

WRAPPER STATE

가지고 있는 것

  • 열려 있는 file object 또는 보통 tpool로 보호된 proxy
  • offset, length, exists extent list
  • 이번 backup의 reference/backend snapshot ID
  • in-use snapshot을 adopt했다면 Cinder snapshot ID
NOT IN MEMORY

가지고 있지 않은 것

  • volume 전체 byte contents
  • 각 extent의 데이터를 미리 읽어 둔 cache
  • 새로운 staging local file
  • 새로운 VM이나 filesystem mount
A B C D X Y Z H I J0 .. 9 · 단순화한 메모리 예시

seek와 read를 숫자로 말하기

volume의 일부가 0..9 = ABCDXYZHIJ라고 가정합니다. {offset: 4, length: 3, exists: true}가 오면 wrapper는 seek(4) 후 read(3)을 실행합니다. 결과는 XYZ이고 cursor는 tell() == 7이 됩니다.

실제 흐름: get extents → extent offset으로 seek → chunk-sized read → _backup_chunk(data, offset)
중요한 오해 방지

CBT는 데이터를 다른 포맷으로 재구성해서 RAM에 쌓는 기능이 아닙니다. driver가 “읽어야 할 byte 범위”를 주면 chunked driver가 그 위치에서 직접 읽습니다. 그래서 CBT 경로에도 새 local staging file이 필요하지 않습니다.

04

Extent의 의미: byte 범위와 exists

Cinder 계약에서 extent는 offset과 length가 byte 단위이며, exists는 그 범위를 백업에 보낼지 판단하는 값입니다. backend API의 같은 이름과 의미가 항상 같지는 않으므로 driver에서 변환해야 합니다.

필드단위 / 값백업에서의 의미
offsetvolume 시작점 기준 bytefile에서 seek(offset)할 위치
lengthbyte 길이해당 범위에서 읽을 최대 byte 수
exists=True할당/변경 범위반드시 읽고 저장합니다. data→zero 변경도 포함됩니다.
exists=Falseunallocated / sparse 범위백업 driver는 보통 건너뜁니다. 단, incremental discard를 이 값으로 그대로 버리면 안 됩니다.
[]와 None서로 다른 결과[]는 “변경 없음”, None은 “지원 안 함/계산 실패”이며 fallback 신호입니다.
Ceph의 native flag와 Cinder shipping contract는 다르다

Ceph diff_iterate callback의 exists=False는 incremental에서 discard/data→zero 변화일 수 있습니다. RBD driver는 incremental에서는 이런 extent를 exists=True로 바꿔 zero bytes도 전송합니다. 그래야 restore 시 parent의 오래된 data가 남지 않습니다. 반대로 full allocation-map에서는 진짜 never-written hole만 생략합니다.

full allocation map

from_snapshot=None은 “target snapshot에 할당된 영역을 알려 달라”는 뜻입니다. 실제로 할당되어 0 byte가 들어 있는 영역은 값이 0이어도 포함될 수 있고, never-written hole은 생략될 수 있습니다.

incremental diff

base와 target 사이에 backend가 보고한 모든 변경을 보냅니다. data→zero, discard, overwrite 모두 restore에 영향을 줄 수 있으므로 “값이 0처럼 보인다”는 이유로 생략하지 않습니다.

인접하고 같은 종류인 extent는 payload를 줄이기 위해 합친다
[{offset: 0,        length: 4 * MiB, exists: true},
 {offset: 4 * MiB,  length: 4 * MiB, exists: true},
 {offset: 12 * MiB, length: 4 * MiB, exists: true}]

→ [{offset: 0, length: 8 * MiB, exists: true},
   {offset: 12 * MiB, length: 4 * MiB, exists: true}]

0–4 MiB와 4–8 MiB는 합쳐지지만, 8–12 MiB hole을 건너뛰고 12–16 MiB까지 합치면 안 됩니다. 합쳐진 extent는 storage object/chunk 크기와 같은 개념도 아닙니다.

05

저장 형식과 metadata: 두 곳에 나누어 저장된다

CBT가 extent를 계산한다고 해서 extent list 자체가 backup repository의 데이터 object가 되는 것은 아닙니다. 실제 byte object와 복원용 metadata, 다음 CBT reference 정보는 서로 다른 경로로 기록됩니다.

BACKUP REPOSITORY · S3 / SWIFT

_write_metadata가 쓰는 JSON object

chunkeddriver는 실제 byte를 별도 object로 저장하고, 같은 backup repository의 container/bucket 안에 별도의 metadata object도 저장합니다. 이 metadata object의 body가 JSON이며, object 이름과 각 object의 offset/length, volume 정보, parent 정보 등 복원에 필요한 실제 필드를 기록합니다. compression/checksum 관련 기존 logic도 이 경로에 남아 있습니다.

저장 위치를 정확히 말하면

제공된 구현에서 _write_metadata(backup, ..., container, ...)는 filename = <backup.service_metadata>_metadata를 만들고 _get_object_writer(container, filename)로 JSON bytes를 씁니다. 따라서 Swift를 쓰면 설정된 backup Swift container 안의 별도 object이고, S3를 쓰면 설정된 backup bucket 안의 별도 object입니다.

즉 각 데이터 object의 S3 object metadata header나 Swift user-metadata field에 JSON을 넣는 방식이 아닙니다. 이 메서드가 하는 일은 JSON을 object body로 저장하는 것입니다. 

{
  "objects": [
    {"chunk-0001": {"offset": 4096, "length": 4096}}
  ],
  "parent_id": "...",
  "volume_meta": "..."
}

위 JSON은 metadata object body의 구조를 이해하기 위한 단순화한 예시이며, 실제 저장 형식의 모든 필드를 나타내지 않습니다.

CINDER DATABASE

_save_cbt_metadata가 DB에 쓰는 값

제공된 구현 diff에서는 Backup.metadata의 cbt_metadata 키에 다음 backup의 기준점과 backend 식별 정보를 JSON 문자열로 저장합니다. 변경 extent 목록 자체를 DB에 저장하는 구조는 확인되지 않습니다. 

{
  "reference_snapshot": "backend-id",
  "cbt_backend": "host-backend",
  "reference_snapshot_cinder_id": "..."  // adopt한 경우만
}

cbt_backend는 구현에서 volume host의 backend 문자열에서 파생되며, 항상 literal ceph나 pure라고 단정할 수 없습니다.

스펙과 구현의 표현 차이

스펙은 framework가 backup metadata에 reference를 저장한다고 설명하지만, 제공된 실제 consumption diff에서는 chunkeddriver의 _save_cbt_metadata가 Backup.metadata를 저장합니다. 문서나 코드 설명에서는 “framework가 관리한다”와 “현재 코드에서 실제 write를 수행하는 위치”를 구분해 말하는 것이 정확합니다.

06

Snapshot lifecycle: reference를 언제 만들고 지우는가

reference는 데이터를 읽은 뒤에 만드는 것이 아니라, 읽을 시점과 맞는 point-in-time을 먼저 확보한 뒤 사용합니다. 특히 in-use volume에서는 백업이 이미 만든 temporary snapshot을 adopt해 읽은 데이터와 reference를 일치시킵니다.

  1. FULLreference 생성detached면 driver snapshot, in-use면 temp snapshot adopt
  2. READdata 읽기같은 point-in-time의 device file
  3. NEXTreference 기록Backup.metadata의 cbt_metadata
  4. INCREMENTAL새 reference + diffparent 기준점과 새 기준점 비교
  5. CLEANUP이전 기준점 삭제adopted/driver-created provenance에 맞춰 삭제
상황reference 처리cleanup
available volume fullcreate_cbt_snapshot으로 backend snapshot 생성다음 backup에 의해 superseded되면 delete_cbt_snapshot
in-use volume백업용 temporary Cinder snapshot의 provider_id를 adopt성공 시 temp_snapshot ownership을 CBT로 넘기고, 나중에 Cinder snapshot API로 삭제
incremental diff 실패새로 만든 driver reference만 orphan으로 정리adopted snapshot은 temp-snapshot cleanup과 중복 삭제하지 않음
parent reference 유실re-bootstrap하지만 parent가 있으므로 dense full scan새 reference 성공 후 오래된 reference를 best-effort 삭제
새 VM이나 mount가 필요한가?

제공된 구현은 백업마다 새 VM을 만드는 흐름이 아닙니다. snapshot을 export할 때 backend가 허용하는 COW clone/temporary volume을 만들고, backup host가 block device로 attach해 읽은 뒤 정리합니다. RBD는 Ceph RBD block interface로 연결하고, Everpure는 driver variant에 따라 iSCSI/FC/NVMe 경로를 사용합니다.

07

RBD의 별도 버그 수정: snapshot export/attach

이것이 사용자가 말한 “CBT 전에 먼저 고친 부분”입니다. CBT를 설명하기 전에, 왜 이 변경을 독립 CR로 두었는지부터 말해야 합니다.

문제

backup_use_temp_snapshot 경로가 선택되면 backup manager는 snapshot을 attach해 읽으려 합니다. 그런데 RBD driver는 create_export_snapshot와 initialize_connection_snapshot을 구현하지 않았고 BaseVD 기본값은 None을 반환했습니다. 그 결과 attach 정보가 비어 뒤 단계에서 TypeError가 발생할 수 있었습니다. 이 문제는 CBT를 사용하지 않는 snapshot backup에도 존재하므로 CBT CR에 섞지 않았습니다.

수정 방법

  1. snapshot ID로부터 deterministic temporary volume object를 만듭니다.
  2. snapshot의 backend name을 source로 사용해 COW RBD clone을 만듭니다.
  3. export image는 Cinder volume이 아니므로 _clone_image를 사용하고 _setup_volume을 건너뜁니다.
  4. backup host가 일반 initialize_connection으로 clone을 attach합니다.
  5. 연결을 끊은 뒤 remove_export_snapshot에서 temporary clone을 삭제합니다.

왜 _clone을 분리했는가?

기존 _clone은 volume 생성 뒤 replication/type 설정을 위해 _setup_volume을 호출합니다. snapshot export image에는 Cinder volume type을 적용하면 안 되므로 clone 자체만 하는 _clone_image를 분리했습니다. transient Volume object는 DB에 저장하지 않습니다. 

create_export_snapshot(...):
    temp = _snapshot_temp_volume(snapshot)
    _clone_image(temp, rbd_pool,
                 snapshot.volume_name,
                 snapshot.provider_id or snapshot.name)

initialize_connection_snapshot(...):
    return initialize_connection(_snapshot_temp_volume(snapshot), connector)

이 bugfix에서는 backup_use_temp_snapshot을 강제로 True로 바꾸지 않고 configuration 선택으로 남겼습니다. 이후 CBT 구현에서 RBD가 CBT를 위해 True를 반환하도록 한 점이 lifecycle상의 추가 변화입니다.

08

RBD CBT 구현: librbd diff_iterate

RBD CBT CR은 Cinder driver 계약의 세 메서드를 Ceph librbd primitive에 매핑합니다. snapshot identifier는 RBD snapshot name이고, 일반 Cinder snapshot도 provider_id에 backend name을 노출하도록 맞춥니다.

메서드실제 동작실패 시
create_cbt_snapshotRBDVolumeProxy를 열고 rbd_image.create_snap(snapshot) 실행. 반환값은 snapshot name.exception을 삼키고 None 반환 → plain full fallback
get_cbt_extentstarget snapshot 시점으로 image를 열고 diff_iterate(start, scan_len, from_snapshot, callback) 호출partial/추측 결과 대신 None → incremental fallback/re-bootstrap
delete_cbt_snapshotremove_snap(snapshot) 실행. ImageNotFound/ObjectNotFound는 이미 삭제된 것으로 처리best-effort warning만 남김
제공된 RBD 구현의 핵심을 설명하기 위한 축약 코드
with RBDVolumeProxy(self, volume.name,
                    snapshot=to_snapshot) as image:
    size = image.size()
    start = offset or 0
    scan_len = min(length, size - start) if length else size - start

    def callback(ext_offset, ext_length, ext_exists):
        if from_snapshot is None and not ext_exists:
            return                    # full allocation-map hole
        # incremental에서는 discard도 ship해야 하므로 True로 기록
        append_or_merge(ext_offset, ext_length, exists=True)

    image.diff_iterate(start, scan_len, from_snapshot, callback)
return volume_utils.window_cbt_page(extents, offset, length, marker, limit)

full

from_snapshot=None을 librbd에 넘겨 allocation map을 얻습니다. exists=False hole은 생략하고, 보고된 allocated extent는 모두 True로 저장합니다. 그래서 첫 full도 sparse하게 만들 수 있습니다.

incremental

from_snapshot과 to_snapshot 사이의 callback 결과를 모두 보냅니다. Ceph가 discard를 False로 알려도 Cinder 출력에서는 True로 바꾸어 zero bytes를 전송합니다.

window 처리

RBD는 offset과 length를 scan 시작점과 길이로 diff_iterate에 내려 보낼 수 있습니다. 다만 Ceph API 호출에 고정 CBT block-size 인자를 넣는 구현은 아닙니다. whole_object=False 기본 동작으로 object 내부 delta도 반환할 수 있으므로 “항상 4 MiB 단위”라고 말하면 안 됩니다.

09

Everpure CBT 구현: FlashArray volumes/diff

Everpure는 같은 Cinder 계약을 FlashArray API에 연결합니다. 다만 framework가 주는 opaque name hint를 그대로 array 이름으로 쓰지 않고, 안전하고 길이가 제한된 deterministic snapshot name으로 변환합니다.

단계Everpure 구현설명

Everpure가 모든 결과를 exists=True로 표시하는 이유

FlashArray의 volumes/diff가 반환한 범위는 이 backup에 보내야 할 영역이라고 보고, “반환되지 않은 영역”을 unchanged/skip으로 취급합니다. 이 방식이 data→unallocated/trim 변화를 diff로 보고한다는 array 동작에 의존하므로, 다른 backend로 이 패턴을 복사할 때는 그 보장을 확인해야 합니다.

snapshot attach는 어떻게 다른가?

Everpure FlashArray snapshot은 직접 attach하지 않고 Reference(name=snapshot)로 temporary COW volume을 materialize합니다. 이후 normal volume connection path를 재사용하고, backup이 끝나면 temporary volume을 destroy합니다. 이 CR에서 CBT와 snapshot attach, backup_use_temp_snapshot=True를 함께 넣은 점이 RBD의 분리 방식과 다릅니다.

제공된 driver variant에는 iSCSI, FC, NVMe가 있으며, 이는 data path의 예입니다. backend management API와 host data access path를 하나로 단정하면 안 됩니다.

Chunk size와 CBT diff block size는 다르다

“1 MiB로 diff한다”와 “backup object가 1 MiB다”는 같은 말이 아닙니다. backend가 변경 범위를 정하는 크기, backup object를 나누는 크기, 기존 SHA 비교의 단위가 각각 다를 수 있습니다.

설정/개념제공된 코드·문서에서의 의미CBT에서의 역할

backup_swift_block_size / backup_s3_block_size기본 32768 bytes = 32 KiB기존 full-scan incremental의 SHA 비교 granularity. CBT incremental에서는 SHA 비교를 건너뜀

RBD diff granularitydiff_iterate 호출에 별도 CBT block-size 인자 없음librbd가 반환한 extent를 merge하고 backup chunk size로 다시 나눔
검증된 구현상의 작은 주의점

CBT 경로는 SHA file을 만들지 않지만, 제공된 chunkeddriver 코드에는 시작 시 chunk_size_bytes % sha_block_size_bytes validation이 남아 있습니다. 따라서 “CBT에서는 SHA를 안 쓰니 관련 설정 검증도 모두 사라진다”고 말하면 안 됩니다. 이는 현재 diff에서 확인되는 동작입니다.

12

Restore: offset write와 sparse full의 차이

CBT가 restore 전용 포맷을 새로 만드는 것은 아닙니다. 기존 object metadata의 offset을 사용해 chain을 재구성하고, 필요한 위치에 bytes를 씁니다. 단, sparse full의 “전혀 저장되지 않은 hole”은 예외 처리가 필요합니다.

incremental에서 data→zero

변경 extent가 exists=True로 전달되고, backup은 실제 device에서 zero bytes를 읽어 저장합니다. restore 때 그 zero object를 해당 offset에 쓰므로 parent의 옛 data가 남지 않습니다.

sparse full의 hole

첫 full allocation map은 never-written hole을 object로 저장하지 않을 수 있습니다. 새 volume은 원래 zero이지만, 기존 volume에 restore하면 stale data가 남을 수 있습니다. 그래서 metadata에 sparse를 기록하고 기존 target일 때만 uncovered 범위를 zero-fill합니다. 

if metadata.get('sparse') and not volume_is_new:
    _zero_fill_uncovered(volume_file, metadata_objects,
                         int(backup['size']) * units.Gi)

# 이 zero-fill은 sparse FULL에만 적용됩니다.
# incremental의 모든 unchanged hole을 일괄 zero-fill하는 동작이 아닙니다.
re-bootstrap은 왜 dense여야 하는가?

CBT parent의 reference가 사라지면 새 reference를 만들고 한 번 full scan으로 체인을 복구합니다. 이 backup은 여전히 parent_id를 가진 chain의 다음 레이어이므로 sparse allocation map을 보내면 parent에 남아 있는 stale data를 덮지 못합니다. 따라서 recovery re-bootstrap은 allocation map이 가능해도 dense scan이어야 합니다.

13

REST API와 paging: 외부 도구가 extent를 묻는 경로

os-list_changed_blocks는 cinder-backup 내부뿐 아니라 외부 backup tool도 같은 backend CBT 정보를 조회하게 하려는 스펙상의 volume action입니다. 제공된 계약은 microversion 3.72와 byte window, marker/limit을 정의합니다.

REQUEST
POST /v3/{project_id}/volumes/{volume_id}/action
OpenStack-API-Version: volume 3.72

{
  "os-list_changed_blocks": {
    "base_snapshot_id": "...",  // full이면 생략/null
    "target_snapshot_id": "...",
    "offset": 0,
    "length": 1048576,
    "marker": 0,
    "limit": 100
  }
}
RESPONSE
{
  "changed_blocks": [
    {"offset": 4096, "length": 4096, "exists": true}
  ],
  "changed_blocks_next_marker": 8192
}

None이나 지원하지 않는 backend는 API layer에서 409 Conflict로 표시합니다.

현재 제공된 구현에서 확인한 paging 범위

driver는 마지막에 window_cbt_page를 적용하고, API layer도 결과를 다시 clip해 next marker를 계산합니다. REST API는 기본 changed_blocks_max_limit=1000으로 bounded limit을 driver에 전달합니다. 다만 제공된 내부 backup consumption 호출은 window/marker/page를 넘기지 않고 전체 extent list를 받아 _backup_cbt에서 순회합니다. 또한 Pure diff는 현재 전체 volume diff 후 helper를 적용합니다. 따라서 “RPC로 넘어가는 page는 제한된다”와 “backend/driver 내부가 언제나 page 크기만큼만 메모리에 가진다”를 구분해야 합니다.

스펙과 구현을 섞지 않기

413, CBTPagingRequired, 전용 timeout 같은 항목은 스펙/후속 paging 논의에 등장하지만, 이 문서에서 읽은 두 driver와 backup consumption diff에 모두 구현됐다고 단정하지 않습니다. 실제 API 동작을 말할 때는 확인한 patchset과 배포 버전을 함께 확인해야 합니다.

다른 backend에 적용할 때의 경계

PowerStore에 관해 확인된 범위

Dell 문서는 PowerStore snapshot-differential이 replication에 사용된다고 설명합니다. 그러나 그 사실만으로 Cinder driver가 호출할 수 있는 public changed-block extent API가 존재한다고 증명되지는 않습니다. 따라서 “PowerStore도 private API만 있다”거나 “당장 CBT driver를 만들 수 있다”고 단정하지 않습니다.

Dell PowerStore replication theory of operation

PowerFlex와 data path

PowerFlex처럼 SDC가 필요한 환경에서는 관리 API와 실제 block data를 읽는 host/client 경로를 구분해야 합니다. CBT driver가 backend diff를 가져오는 위치, backup host가 block device를 읽는 위치, SDC가 설치된 위치가 배포 구성에 따라 다를 수 있습니다.

여기서는 특정 제품의 미확인 API를 가정하지 않고, Cinder driver contract와 supported data path를 먼저 확인하는 것이 안전합니다.
